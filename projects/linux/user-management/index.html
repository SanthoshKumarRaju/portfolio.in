User Management

•server
Summary

The User Management module covers the complete process of managing users on a Linux server, starting with understanding different user types and creating or modifying accounts using tools like useradd, usermod, and userdel. It also explains group management and how to implement least-privilege access using groups and sudo roles. The module focuses on security practices such as password policies, SSH key authentication, and protecting home directory permissions. Additionally, it includes monitoring login activity, auditing user accounts, and managing resource limits. Finally, it teaches how to lock, disable, or expire accounts to maintain a secure and production-ready server environment.

User Management

Goal: Understand different types of Linux users and how user identities control access to system resources.

  1. What is a Linux User
    A Linux user represents an identity that can log into the system and access files or run programs. Linux is designed as a multi-user operating system, meaning multiple users can operate on the same machine.
    Each user has:
    • a username
    • a user ID (UID)
    • a home directory
    • a default shell
    Example user information:
    username: santhosh
    UID: 1001
    home directory: /home/santhosh
    shell: /bin/bash
  2. Viewing the Current User
    To check the current logged-in user:
    whoami
    Example output:
    santhosh
  3. Checking Logged-in Users
    Linux can support multiple simultaneous user sessions.
    Check active users:
    who
    Example output:
    santhosh pts/0 2026-03-13 10:12
    admin    pts/1 2026-03-13 10:20
  4. Main Types of Linux Users
    Linux typically categorizes users into three main types:
    • Root user
    • System users
    • Regular users
    Each type has different roles and permissions.
  5. Root User (Administrator)
    The root user is the superuser with full administrative privileges.
    Characteristics:
    • UID = 0
    • can modify any file
    • can install software
    • can manage users
    • can control system services
    Example switching to root:
    sudo -i
    Example root prompt:
    root@server:~#
  6. System Users
    System users are accounts used by background services and applications.
    Examples include:
    • mysql
    • nginx
    • www-data
    • daemon
    These accounts normally do not log in interactively.
    View system users:
    cat /etc/passwd
    Example output:
    mysql:x:110:114:MySQL Server:/nonexistent:/bin/false
    Notice that system users often have:
    • no login shell
    • restricted access
  7. Regular Users
    Regular users are human users who log into the system.
    Example:
    • developers
    • system administrators
    • operators
    Example user entry:
    santhosh:x:1001:1001:Santhosh:/home/santhosh:/bin/bash
    These users have:
    • a home directory
    • a login shell
    • restricted system privileges
  8. User ID (UID)
    Each Linux user has a unique numeric identifier called UID.
    Example checking UID:
    id
    Example output:
    uid=1001(santhosh) gid=1001(santhosh) groups=1001(santhosh),27(sudo)
    UID ranges usually follow this pattern:
    UID Range Purpose
    0 root user
    1–999 system users
    1000+ regular users
  9. User Home Directories
    Each user normally has a home directory.
    Example:
    /home/santhosh
    Check home directory:
    echo $HOME
    Example output:
    /home/santhosh
    Home directories store:
    • user files
    • personal configuration
    • SSH keys
    • application settings
  10. User Shell
    The shell defines how users interact with the system.
    Common shells include:
    • /bin/bash
    • /bin/zsh
    • /bin/sh
    Check user shell:
    echo $SHELL
    Example output:
    /bin/bash
  11. Why User Management Matters
    Proper user management ensures system security.
    Benefits include:
    • controlled system access
    • accountability for actions
    • protection of sensitive data
    • separation of administrative duties
    User identities form the foundation of Linux security.
Completion check: You should now understand different Linux user types including root users, system users, and regular users and how user identities control access to system resources.

Goal: Learn how to create, modify, secure, and remove user accounts on Linux systems using user management commands.

  1. Why User Management is Important
    User management is essential for maintaining a secure multi-user environment.
    Administrators must control:
    • who can access the system
    • what resources users can access
    • how user accounts are configured
    Proper user management helps enforce security policies.
  2. Creating a New User
    The primary command used to create users is:
    sudo useradd username
    Example:
    sudo useradd developer
    Verify the user:
    id developer
    Example output:
    uid=1002(developer) gid=1002(developer) groups=1002(developer)
  3. Creating a User with Home Directory
    Many distributions automatically create a home directory, but you can ensure it using:
    sudo useradd -m developer
    Check the directory:
    ls /home
    Example output:
    developer
    santhosh
  4. Setting a User Password
    After creating a user, assign a password:
    sudo passwd developer
    Example output:
    Enter new UNIX password:
    Retype new UNIX password:
    passwd: password updated successfully
  5. Using adduser Command
    Some Linux systems provide the interactive command:
    sudo adduser developer
    This command automatically:
    • creates the home directory
    • sets user password
    • assigns default groups
  6. Viewing User Information
    User information is stored in: 
    /etc/passwd
    Check specific user entry:
    grep developer /etc/passwd
    Example output:
    developer:x:1002:1002::/home/developer:/bin/bash
    Fields represent:
    • username
    • password placeholder
    • UID
    • GID
    • home directory
    • login shell
  7. Modifying User Accounts
    User accounts can be modified using:
    sudo usermod
    Example changing username:
    sudo usermod -l devuser developer
    Change home directory:
    sudo usermod -d /home/devuser devuser
  8. Adding Users to Groups
    Users can be assigned additional groups.
    Example:
    sudo usermod -aG sudo developer
    Verify:
    groups developer
    Example output:
    developer : developer sudo
  9. Locking and Unlocking User Accounts
    Administrators may temporarily disable accounts.
    Lock account:
    sudo passwd -l developer
    Unlock account:
    sudo passwd -u developer
    Locked users cannot log in.
  10. Deleting User Accounts
    Remove user account:
    sudo userdel developer
    Remove user and home directory:
    sudo userdel -r developer
    Verify removal:
    id developer
    Example output:
    id: developer: no such user
  11. Creating Service Accounts
    Service accounts are used by applications.
    Example:
    sudo useradd -r -s /usr/sbin/nologin nginx
    Explanation:
    • -r → system user
    • -s nologin → prevents login
    Service accounts improve system security.
  12. Password Aging and Expiration
    Administrators can enforce password expiration.
    Example:
    sudo chage -l developer
    Example output:
    Last password change : Mar 12, 2026
    Password expires : Jun 10, 2026
    Set expiration policy:
    sudo chage -M 90 developer
    This forces password changes every 90 days.
  13. Security Best Practices for User Accounts
    Administrators should follow these practices:
    • remove unused accounts
    • avoid shared user accounts
    • use strong passwords
    • enforce password rotation policies
    • create service accounts for applications
    These practices help secure production servers.
Completion check: You should now understand how to create, modify, secure, and remove user accounts using Linux user management commands.

Goal: Understand how Linux groups work and how administrators manage groups to control access to shared resources.

  1. What is a Linux Group
    A group is a collection of users who share common access permissions. Groups allow administrators to manage permissions for multiple users at the same time. Instead of assigning permissions to each user individually, permissions can be assigned to the group.
    Example:
    developers
    admins
    devops
    Users added to these groups automatically inherit the group permissions.
  2. Primary and Secondary Groups
    Each Linux user belongs to:
    • a primary group
    • one or more secondary groups
    Primary group:
    • assigned when the user is created
    • used for default file ownership
    Secondary groups:
    • provide additional permissions
    • allow collaboration between users
    Check group membership:
    groups
    Example output:
    santhosh : santhosh sudo docker devops
  3. Viewing All Groups
    Linux stores group information in: 
    /etc/group
    To view all groups:
    cat /etc/group
    Example output:
    root:x:0:
    sudo:x:27:santhosh
    docker:x:999:devops
    Each entry contains:
    • group name
    • password placeholder
    • group ID (GID)
    • members
  4. Creating a New Group
    Groups can be created using the groupadd command.
    sudo groupadd developers
    Verify group creation:
    grep developers /etc/group
    Example output:
    developers:x:1003:
  5. Adding Users to a Group
    Users can be added to groups using the usermod command.
    Example:
    sudo usermod -aG developers santhosh
    Verify:
    groups santhosh
    Example output:
    santhosh : santhosh developers sudo
    The user now belongs to the developers group.
  6. Removing Users from a Group
    To remove a user from a group:
    sudo gpasswd -d santhosh developers
    Verify:
    groups santhosh
  7. Changing Group Ownership of Files
    Group ownership determines which users can access files.
    Example:
    sudo chgrp developers project.txt
    Verify:
    ls -l project.txt
    Example output:
    -rw-r--r-- 1 santhosh developers 1024 Mar 14 project.txt
  8. Deleting a Group
    Unused groups can be removed.
    Example:
    sudo groupdel developers
    Verify deletion:
    grep developers /etc/group
  9. Creating Collaborative Project Directories
    Groups are often used for team collaboration.
    Example directory setup:
    sudo mkdir /project
    sudo chgrp developers /project
    sudo chmod 2775 /project
    Explanation:
    • 2 → SGID bit
    • files inherit group ownership
  10. Checking Group IDs
    Each group has a numeric identifier called GID.
    Check group information:
    getent group developers
    Example output:
    developers:x:1003:santhosh
  11. Best Practices for Group Management
    Administrators should follow these guidelines:
    • use groups to manage shared resources
    • avoid giving permissions to individual users
    • review group memberships regularly
    • remove unused groups
    • apply least privilege principle
    These practices improve security and simplify administration.
Completion check: You should now understand how Linux groups work and how administrators manage group membership and permissions.

Goal: Understand how Linux stores user account information, password hashes, and group membership data using system configuration files.

  1. Introduction to Linux Account Files
    Linux stores user and group information in several configuration files located in the /etc directory.
    The most important files are:
    • /etc/passwd
    • /etc/shadow
    • /etc/group
    These files define:
    • user identities
    • password authentication
    • group membership
    • user privileges
  2. The /etc/passwd File
    The /etc/passwd file contains basic user account information.
    View the file:
    cat /etc/passwd
    Example output:
    santhosh:x:1001:1001:Santhosh:/home/santhosh:/bin/bash
    Each line represents one user account.
  3. Understanding /etc/passwd Fields
    The /etc/passwd file contains seven fields separated by colons.
    Example:
    santhosh:x:1001:1001:Santhosh:/home/santhosh:/bin/bash
    Field explanation:
    Field Description
    Username Login name of the user
    Password placeholder Usually "x", indicating password stored in /etc/shadow
    UID User ID
    GID Primary group ID
    Description User information or comment
    Home directory User home directory
    Login shell Default command shell
  4. The /etc/shadow File
    Passwords are not stored directly in /etc/passwd.
    Instead they are stored securely in:
    /etc/shadow
    View the file (requires root privileges):
    sudo cat /etc/shadow
    Example output:
    santhosh:$6$randomhashvalue:19420:0:99999:7:::
    This file contains encrypted password hashes.
  5. Understanding /etc/shadow Fields
    Example entry:
    santhosh:$6$hashvalue:19420:0:99999:7:::
    Field explanation:
    Field Description
    Username User login name
    Password hash Encrypted password
    Last password change Days since password change
    Minimum password age Days before password change allowed
    Maximum password age Password expiration period
    Warning period Password expiration warning days
  6. Password Hash Algorithms
    Linux stores passwords using secure hash algorithms.
    Example hash format:
    $6$hashvalue
    Meaning:
    Prefix Algorithm
    $1$ MD5
    $5$ SHA-256
    $6$ SHA-512
    Modern systems typically use SHA-512.
  7. The /etc/group File
    Group membership information is stored in: 
    /etc/group
    View group file:
    cat /etc/group
    Example output:
    developers:x:1003:santhosh,alice
  8. Understanding /etc/group Fields
    Example:
    developers:x:1003:santhosh,alice
    Field explanation:
    Field Description
    Group name Name of the group
    Password placeholder Usually unused
    GID Group ID
    Members Users belonging to the group
  9. Checking User Information
    To view detailed user information:
    id santhosh
    Example output:
    uid=1001(santhosh) gid=1001(santhosh) groups=1001(santhosh),27(sudo)
  10. Security of Account Files
    These files have restricted permissions.
    Check shadow file permissions:
    ls -l /etc/shadow
    Example output:
    -rw-r----- 1 root shadow 1200 Mar 10 /etc/shadow
    Only root and privileged programs can read this file.
  11. Why These Files Matter
    Understanding these files is important for:
    • user account management
    • authentication troubleshooting
    • security auditing
    • server administration
    System administrators often inspect these files when debugging login problems or investigating security issues.
Completion check: You should now understand how Linux stores user accounts, password hashes, and group information in system files.

Goal: Understand how the sudo command allows controlled administrative privileges and how to configure secure privilege delegation.

  1. Why Privilege Delegation is Needed
    Linux systems restrict administrative privileges to the root user. However, system administrators often need to allow certain users to perform administrative tasks without giving full root access. The sudo command solves this problem by allowing controlled privilege delegation.
    Benefits of sudo:
    • improves security
    • provides activity logging
    • limits administrative privileges
  2. What is the sudo Command
    The sudo command allows a permitted user to run a command as root or another user.
    Example:
    sudo apt update
    Example output:
    [sudo] password for santhosh:
    Reading package lists... Done
    The system temporarily grants elevated privileges.
  3. Checking User Sudo Privileges
    To view commands a user can run using sudo:
    sudo -l
    Example output:
    User santhosh may run the following commands on this host:
      (ALL : ALL) ALL
    This means the user can execute any command using sudo.
  4. Adding Users to the sudo Group
    Many Linux distributions grant sudo access through group membership.
    Example adding user to sudo group:
    sudo usermod -aG sudo developer
    Verify membership:
    groups developer
    Example output:
    developer : developer sudo
  5. The /etc/sudoers File
    The sudo configuration file is located at: 
    /etc/sudoers
    This file defines which users and groups can run commands with elevated privileges.
    Example entry:
    %sudo ALL=(ALL:ALL) ALL
    Meaning:
    • members of sudo group
    • can execute any command
    • as any user
  6. Editing the sudoers File Safely
    The sudoers file should always be edited using:
    sudo visudo
    Why visudo?
    • checks syntax errors
    • prevents configuration mistakes
    • protects the system from misconfiguration
  7. Granting Specific Command Permissions
    Administrators can limit which commands users can run.
    Example:
    developer ALL=(ALL) /usr/bin/systemctl restart nginx
    This allows the developer user to restart nginx but not run other administrative commands.
  8. Running Commands as Another User
    Sudo can execute commands as another user.
    Example:
    sudo -u nginx whoami
    Example output:
    nginx
    This runs the command as the nginx user.
  9. Switching to Root Shell
    To open a root shell:
    sudo -i
    Example output:
    root@server:~#
    This grants full root access until the session ends.
  10. Sudo Logging and Auditing
    Sudo logs all executed commands.
    Logs are stored in:
    /var/log/auth.log
    Check logs:
    sudo tail /var/log/auth.log
    Example output:
    sudo: santhosh : TTY=pts/0 ; COMMAND=/usr/bin/apt update
    This helps administrators audit system activity.
  11. Security Best Practices for Sudo
    Administrators should follow these best practices:
    • avoid giving full sudo access to all users
    • grant only required commands
    • review sudo privileges regularly
    • monitor sudo logs
    Proper sudo configuration prevents privilege escalation attacks.
  12. Real Production Scenario
    Example DevOps environment:
    • developers can restart application services
    • only administrators can modify system configuration
    • all actions are logged
    Example rule:
    %developers ALL=(ALL) /usr/bin/systemctl restart app
    This ensures controlled privilege delegation.
Completion check: You should now understand how Linux sudo controls administrative privileges and how to safely configure privilege delegation.

Goal: Understand how SSH authentication works and how to configure secure remote access using SSH keys and access control policies.

  1. What is SSH
    SSH (Secure Shell) is a protocol used to securely access remote Linux systems over a network.
    Administrators use SSH to:
    • manage remote servers
    • execute commands
    • transfer files
    • perform system administration tasks
    Example connecting to a server:
    ssh user@server-ip
    Example output:
    user@192.168.1.10's password:
  2. Password Authentication
    By default, SSH allows login using passwords.
    Example login process:
    ssh santhosh@server
    Example output:
    santhosh@server's password:
    However, password authentication is vulnerable to:
    • brute force attacks
    • password guessing
    • credential theft
    Therefore, production systems use SSH keys instead.
  3. SSH Key Authentication
    SSH key authentication uses a pair of cryptographic keys:
    • public key
    • private key
    The public key is stored on the server, and the private key remains on the client machine. This method provides stronger security than passwords.
  4. Generating SSH Keys
    Generate SSH key pair:
    ssh-keygen
    Example output:
    Generating public/private rsa key pair.
    Enter file in which to save the key (/home/user/.ssh/id_rsa):
    Default files created:
    ~/.ssh/id_rsa
    ~/.ssh/id_rsa.pub
  5. Understanding Key Files
    Private key: 
    ~/.ssh/id_rsa
    Public key:
    ~/.ssh/id_rsa.pub
    Security rule:
    • never share private keys
    • only distribute public keys
  6. Copying Public Key to Server
    The easiest way to copy the key is:
    ssh-copy-id user@server
    Example output:
    Number of key(s) added: 1
    Now try logging into the machine
    This command adds the public key to:
    ~/.ssh/authorized_keys
  7. Authorized Keys File
    The server stores trusted keys inside: 
    ~/.ssh/authorized_keys
    Example:
    cat ~/.ssh/authorized_keys
    Example output:
    ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...
    Any client with the matching private key can authenticate.
  8. Correct SSH Directory Permissions
    SSH requires strict file permissions.
    Set permissions:
    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/authorized_keys
    Verify:
    ls -ld ~/.ssh
    Example output:
    drwx------ 2 santhosh santhosh 4096 .ssh
  9. Disabling Password Authentication
    For better security, disable password logins.
    Edit SSH configuration:
    sudo nano /etc/ssh/sshd_config
    Change settings:
    PasswordAuthentication no
    PermitRootLogin no
    Restart SSH:
    sudo systemctl restart ssh
  10. Restricting SSH Access
    Administrators can restrict SSH access to specific users.
    Edit configuration:
    AllowUsers santhosh admin
    This prevents other users from logging in via SSH.
  11. Monitoring SSH Login Activity
    Login attempts are recorded in system logs.
    Check authentication logs:
    sudo tail /var/log/auth.log
    Example output:
    Accepted publickey for santhosh from 192.168.1.5
  12. Security Best Practices
    Best practices for SSH security include:
    • use SSH key authentication
    • disable password authentication
    • disable root login
    • restrict login users
    • monitor login logs
    These practices significantly improve server security.
Completion check: You should now understand how SSH authentication works and how to configure secure key-based access for Linux servers.

Goal: Understand how Linux protects user home directories and how to secure personal files, SSH keys, and configuration data.

  1. What is a Home Directory
    Each Linux user has a home directory where personal files, configuration settings, and application data are stored.
    Typical location:
    /home/username
    Example:
    /home/santhosh
    /home/developer
    Home directories allow users to store their files separately from system files.
  2. Viewing Home Directory Permissions
    Check directory permissions:
    ls -ld /home/santhosh
    Example output:
    drwxr-x--- 20 santhosh santhosh 4096 Mar 15 /home/santhosh
    Permission meaning:
    • owner → full access
    • group → limited access
    • others → no access
  3. Securing Home Directory Permissions
    Home directories should not be accessible by other users.
    Recommended permission:
    chmod 700 /home/santhosh
    Verify:
    ls -ld /home/santhosh
    Example output:
    drwx------ 20 santhosh santhosh 4096 /home/santhosh
    This ensures only the user can access their files.
  4. Understanding Hidden Configuration Files
    Home directories contain hidden configuration files.
    List hidden files:
    ls -la
    Example output:
    .bashrc
    .profile
    .ssh
    .gitconfig
    These files store user environment settings.
  5. The .ssh Directory
    The `.ssh` directory stores SSH authentication keys.
    Location:
    ~/.ssh
    View contents:
    ls ~/.ssh
    Example output:
    id_rsa
    id_rsa.pub
    authorized_keys
    known_hosts
  6. SSH Private Key Protection
    Private keys must be protected with strict permissions.
    Set secure permissions:
    chmod 600 ~/.ssh/id_rsa
    Verify:
    ls -l ~/.ssh/id_rsa
    Example output:
    -rw------- 1 santhosh santhosh id_rsa
    Private keys should never be readable by others.
  7. Securing the .ssh Directory
    The SSH directory itself must also be protected.
    Set directory permissions:
    chmod 700 ~/.ssh
    Verify:
    ls -ld ~/.ssh
    Example output:
    drwx------ 2 santhosh santhosh .ssh
    Improper permissions can cause SSH login failures.
  8. Protecting the authorized_keys File
    The authorized_keys file stores public keys allowed to access the server.
    Set correct permissions:
    chmod 600 ~/.ssh/authorized_keys
    Verify:
    ls -l ~/.ssh/authorized_keys
    Example output:
    -rw------- 1 santhosh santhosh authorized_keys
  9. Checking Disk Usage in Home Directory
    Administrators often monitor storage usage.
    Example command:
    du -sh /home/*
    Example output:
    2.1G /home/santhosh
    350M /home/developer
    This helps identify large files or storage issues.
  10. Preventing Unauthorized File Access
    Administrators should ensure that sensitive files are protected.
    Examples:
    • SSH private keys
    • environment variables
    • API credentials
    • application secrets
    Example permission check:
    find /home -type f -perm -o+r
    This finds files readable by all users.
  11. Best Practices for Home Directory Security
    Administrators should follow these practices:
    • restrict home directory permissions
    • protect SSH private keys
    • monitor disk usage
    • remove unused files
    • audit sensitive configuration files
    These practices help maintain secure user environments.
Completion check: You should now understand how Linux home directories are structured and how administrators secure user data and SSH keys.

Goal: Learn how Linux administrators monitor user logins, track activity, audit account usage, and detect suspicious system access.

  1. Why User Monitoring is Important
    Linux servers are often used by multiple users and services.
    Administrators must monitor system access to:
    • detect unauthorized logins
    • investigate security incidents
    • audit user activity
    • identify inactive accounts
    Monitoring helps maintain system security and accountability.
  2. Viewing Currently Logged-In Users
    To see users currently logged into the system:
    who
    Example output:
    santhosh pts/0 2026-03-16 10:20 (192.168.1.5)
    developer pts/1 2026-03-16 10:25 (192.168.1.20)
    Information shown:
    • username
    • terminal session
    • login time
    • remote IP address
  3. Viewing Active User Sessions
    Another useful command is:
    w
    Example output:
    USER     TTY      FROM            LOGIN@   IDLE   JCPU   PCPU WHAT
    santhosh pts/0    192.168.1.5     10:20    2:10   0.03s  0.01s bash
    developer pts/1   192.168.1.20    10:25    0.00s  0.02s  0.01s vim
    This command also shows what each user is currently doing.
  4. Viewing Login History
    To view historical login records:
    last
    Example output:
    santhosh pts/0 192.168.1.5 Mon Mar 16 10:20 still logged in
    developer pts/1 192.168.1.20 Mon Mar 16 10:10 - 10:15 (00:05)
    The command reads information from:
    /var/log/wtmp
  5. Checking Failed Login Attempts
    To view failed login attempts:
    lastb
    Example output:
    root ssh:notty 192.168.1.200 Mon Mar 16 09:10 - 09:10 (00:00)
    These records are stored in:
    /var/log/btmp
    Frequent failures may indicate brute-force attacks.
  6. Viewing Last Login for Each User
    To see the last login time for each user:
    lastlog
    Example output:
    Username     Port     From           Latest
    santhosh     pts/0    192.168.1.5    Mon Mar 16 10:20
    developer    pts/1    192.168.1.20   Mon Mar 16 10:10
    This helps administrators detect inactive accounts.
  7. Checking User Login Sessions
    View all sessions for a specific user:
    last santhosh
    Example output:
    santhosh pts/0 192.168.1.5 Mon Mar 16 10:20 still logged in
    santhosh pts/2 192.168.1.3 Sun Mar 15 09:10 - 09:40
  8. Monitoring Authentication Logs
    Linux records login attempts and sudo activity in log files.
    Check authentication logs:
    sudo tail /var/log/auth.log
    Example output:
    Accepted publickey for santhosh from 192.168.1.5
    Failed password for admin from 192.168.1.200
    These logs are essential for security investigations.
  9. Tracking Sudo Usage
    Sudo commands are logged for auditing.
    Example log entry:
    sudo: santhosh : COMMAND=/usr/bin/apt update
    Check sudo activity:
    grep sudo /var/log/auth.log
    This shows administrative actions performed by users.
  10. Monitoring Active Processes by User
    Administrators may check processes started by users.
    Example:
    ps -u santhosh
    Example output:
    PID  TTY   TIME  CMD
    2043 pts/0 00:00 bash
    2201 pts/0 00:00 vim
    This helps identify suspicious activity.
  11. Detecting Inactive Accounts
    Unused accounts should be reviewed or removed.
    Example command:
    lastlog | grep "Never logged in"
    Inactive accounts may pose security risks.
  12. Security Best Practices for User Auditing

Goal: Learn how Linux administrators control system resource usage by setting limits on CPU, memory, open files, and processes for users and groups.

  1. Why Resource Limits Are Important
    In multi-user Linux systems, multiple users and services share the same system resources.
    Without limits, a single user could:
    • consume all CPU resources
    • open too many files
    • create excessive processes
    • exhaust system memory
    Resource limits protect system stability.
  2. Understanding ulimit
    Linux provides a command called ulimit to control resource usage for a user session.
    Check current limits:
    ulimit -a
    Example output:
    core file size          (blocks, -c)  0
    data seg size           (kbytes, -d)  unlimited
    file size               (blocks, -f)  unlimited
    open files                      (-n)  1024
    max user processes              (-u)  4096
    stack size              (kbytes, -s)  8192
  3. Types of Resource Limits
    Linux supports multiple resource limits.
    Common examples:
    • maximum open files
    • maximum processes
    • maximum memory usage
    • maximum CPU time
    • maximum file size
    These limits protect system performance.
  4. Soft Limits vs Hard Limits
    Linux defines two types of limits:
    • Soft limit
    • Hard limit
    Soft limit:
    • default limit applied to users
    • can be changed by the user
    Hard limit:
    • maximum allowed limit
    • only root can modify
  5. Setting Temporary Limits
    Limits can be changed temporarily for a session.
    Example limiting open files:
    ulimit -n 200
    Verify:
    ulimit -n
    Example output:
    200
    This limit applies only to the current session.
  6. Permanent Resource Limits
    Permanent limits are configured in: 
    /etc/security/limits.conf
    Edit configuration file:
    sudo nano /etc/security/limits.conf
    Example configuration:
    developer soft nofile 2048
    developer hard nofile 4096
    This sets limits for the developer user.
  7. Understanding limits.conf Fields
    Example rule:
    developer soft nproc 100
    Field explanation:
    Field Description
    developer user or group name
    soft soft limit
    nproc maximum processes
    100 limit value
  8. Applying Limits to Groups
    Limits can also be applied to groups.
    Example:
    @developers hard nproc 200
    The "@" symbol indicates a group rule.
    This limits the number of processes developers can create.
  9. PAM and Resource Limits
    Linux uses PAM (Pluggable Authentication Modules) to enforce limits.
    Ensure the limits module is enabled:
    cat /etc/pam.d/common-session
    Look for:
    session required pam_limits.so
    This ensures limits.conf rules are applied.
  10. Monitoring System Resource Usage
    Administrators often monitor resource consumption.
    Check running processes:
    top
    Example output:
    PID USER PR NI VIRT RES SHR S %CPU %MEM TIME+ COMMAND
    2043 santhosh 20 0 120m 10m 2m S 0.3 0.5 00:00 bash
  11. Preventing Fork Bomb Attacks
    A fork bomb is a malicious script that creates infinite processes.
    Example of a fork bomb:
    :(){ :|:& };:
    Resource limits prevent these attacks.
    Example limit:
    * hard nproc 100
    This restricts maximum processes per user.
  12. Best Practices for Resource Limits
    < Administrators should follow these practices:
    • limit maximum processes per user
    • restrict open file limits
    • monitor system resource usage
    • configure limits for shared servers
    These practices protect server stability.
  13. Production Scenario
    Example production configuration:
    * soft nofile 4096
    * hard nofile 8192
    * hard nproc 200
    This ensures that users cannot exhaust system resources.
Completion check: You should now understand how Linux administrators control system resources using ulimit and limits.conf.

Goal: Understand best practices used in production Linux servers to secure user accounts, manage privileges, and prevent unauthorized access.

  1. Principle of Least Privilege
    One of the most important security principles is the least privilege principle. Users should only receive the minimum permissions required to perform their tasks.
    Benefits:
    • reduces risk of accidental system damage
    • limits impact of compromised accounts
    • protects sensitive system files
    Example insecure permission: 
    chmod 777 file.txt
    Secure alternative:
    chmod 640 file.txt
  2. Disable Direct Root Login
    Allowing direct root login increases security risk. Instead, administrators should use sudo.
    Edit SSH configuration:
    sudo nano /etc/ssh/sshd_config
    Set:
    PermitRootLogin no
    Restart SSH:
    sudo systemctl restart ssh
  3. Use SSH Key Authentication
    Password-based SSH logins are vulnerable to brute-force attacks. Instead, use SSH keys.
    Generate key:
    ssh-keygen
    Copy key to server:
    ssh-copy-id user@server
    Disable password authentication:
    PasswordAuthentication no
  4. Restrict SSH Access
    Administrators should limit which users can access the server.
    Edit SSH configuration:
    AllowUsers santhosh admin
    Or allow specific groups:
    AllowGroups devops admins
  5. Remove Unused Accounts
    Unused accounts create security risks.
    Find inactive accounts:
    lastlog
    Remove unused accounts:
    sudo userdel username
    Or disable account:
    sudo passwd -l username
  6. Monitor User Login Activity
    Administrators should regularly monitor login activity.
    Check login history:
    last
    Example output:
    santhosh pts/0 192.168.1.5 Mon Mar 16 10:20 still logged in
    Check failed login attempts:
    lastb
  7. Audit Sudo Usage
    All sudo commands are logged.
    Check sudo logs:
    grep sudo /var/log/auth.log
    Example output:
    sudo: santhosh : COMMAND=/usr/bin/systemctl restart nginx
    This helps track administrative activity.
  8. Implement Strong Password Policies
    Password policies help prevent unauthorized access.
    Configure password expiration:
    sudo chage -M 90 username
    This forces password changes every 90 days.
    Check password policy:
    sudo chage -l username
  9. Use Service Accounts for Applications
    Applications should run under dedicated service accounts.
    Example:
    sudo useradd -r -s /usr/sbin/nologin nginx
    Benefits:
    • isolates applications
    • limits system access
    • improves security
  10. Regularly Review Group Membership
    Users may gain unnecessary privileges over time.
    Check group membership:
    groups username
    Example output:
    username : username sudo docker
    Remove unnecessary groups:
    sudo gpasswd -d username docker
  11. Enable Security Monitoring Tools
    Production servers often use security tools.
    Examples include:
    • fail2ban
    • auditd
    • rkhunter
    • chkrootkit
    Install fail2ban:
    sudo apt install fail2ban
    Fail2ban blocks IP addresses with repeated failed logins.
  12. Regular System Updates
    Keeping the system updated is essential for security.
    Update package lists:
    sudo apt update
    Upgrade packages:
    sudo apt upgrade
    Updates fix vulnerabilities in installed software.
  13. Production Security Checklist
    A secure Linux server should follow these practices:
    • disable root login
    • use SSH key authentication
    • remove inactive users
    • monitor login activity
    • restrict sudo privileges
    • enforce password policies
    • use service accounts
    • install security monitoring tools
    Following these guidelines greatly improves server security.
Completion check: You should now understand production-level security practices for managing Linux user accounts and protecting servers from unauthorized access.
