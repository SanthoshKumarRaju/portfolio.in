Linux Networking - Interfaces

•server

Goal: Understand Docker networking modes, how containers communicate, and how to choose the right network type for real-world use cases.

  1. What is Docker Networking
    Docker networking allows containers to communicate with each other and external systems.
  2. Why Network Modes Matter
    • Isolation
    • Performance
    • Scalability
  3. Types of Docker Networks
    • Bridge
    • Host
    • Overlay
    • None
  4. Bridge Network (Default)
    • Containers get private IP
    • Connected via docker0 bridge
  5. Bridge Example
    docker network create mybridge
docker run --network mybridge nginx
  6. Port Mapping
    docker run -p 8080:80 nginx
  7. Bridge Internals
    • Uses Linux bridge
    • Uses veth pairs
    • NAT for external access
  8. Host Network
    • No isolation
    • Uses host network stack
  9. Host Example
    docker run --network host nginx
  10. Host Mode Benefits
    • High performance
    • No NAT overhead
  11. Host Mode Drawbacks
    • No port isolation
    • Security concerns
  12. Overlay Network
    • Multi-host networking
    • Used in Docker Swarm
  13. Overlay Example
    docker network create -d overlay myoverlay
  14. Overlay Internals
    • Uses VXLAN
    • Encapsulation of packets
  15. None Network
    • No network connectivity
  16. Inspect Networks
    docker network ls
docker network inspect bridge
  17. Container Communication
    • Same network → direct communication
    • Different networks → isolated
  18. DNS in Docker
    • Automatic service discovery
  19. Bridge vs Host vs Overlay
    Mode Scope Isolation
    Bridge Single host Yes
    Host Single host No
    Overlay Multi-host Yes
  20. Docker Networking in Kubernetes
    • Replaced by CNI plugins
  21. Common Issues
    • Port not accessible
    • Containers cannot communicate
    • Wrong network selected
  22. Debugging
    docker network inspect
ip a
ss -tuln
  23. Check Container IP
    docker inspect container_id
  24. Troubleshooting Workflow
    Check network mode
Check container IP
Test connectivity
Check port mapping
  25. Best Practices
    • Use bridge for single-host apps
    • Use overlay for distributed systems
    • Avoid host unless necessary
  26. Golden Debug Rule
    If containers can't talk → check network mode
  27. Real-World Example
    • Microservices → bridge network
    • High-performance app → host mode
    • Cluster → overlay network
  28. Summary
    Docker networking modes define how containers communicate, providing flexibility, isolation, and scalability for modern applications.
Completion check: You should now understand Docker networking modes and how to use them effectively.

Goal: Understand how containers use internal DNS for service discovery and how it works in Docker and Kubernetes environments.

  1. What is Service Discovery
    Service discovery allows services to find each other dynamically using names instead of IP addresses.
  2. Why DNS is Used
    • IP addresses change frequently
    • Names are stable and human-readable
  3. Basic Concept
    frontend → backend-service → resolved via DNS
  4. Docker Internal DNS
    • Built-in DNS server
    • Runs at 127.0.0.11
  5. Docker DNS Example
    docker network create mynet
docker run --name db --network mynet mysql
docker run --network mynet app
    App can reach DB using: 
    db:3306
  6. Check DNS Config in Container
    cat /etc/resolv.conf
  7. DNS Resolution Flow
    Container → Docker DNS → IP resolution
  8. Docker Compose DNS
    • Service names become DNS names
  9. Kubernetes DNS
    • Uses CoreDNS
    • Cluster-wide DNS
  10. Kubernetes Service DNS
    service-name.namespace.svc.cluster.local
  11. Example
    backend.default.svc.cluster.local
  12. Pod DNS Config
    cat /etc/resolv.conf
  13. DNS Search Domains
    • namespace.svc.cluster.local
  14. Service Types
    • ClusterIP → internal DNS
    • Headless → direct pod IP
  15. DNS in Overlay Networks
    • Used for cross-node communication
  16. Benefits
    • Dynamic discovery
    • No hardcoded IPs
  17. Advanced: DNS Load Balancing
    • Multiple IPs returned
  18. Advanced: Headless Services
    • No load balancing
    • Direct pod access
  19. Common Issues
    • Service name not resolving
    • DNS timeout
    • Wrong namespace
  20. Debug DNS in Container
    nslookup service-name
dig service-name
  21. Check CoreDNS (Kubernetes)
    kubectl get pods -n kube-system
  22. Test Connectivity
    ping service-name
curl service-name
  23. Check DNS Logs
    kubectl logs coredns
  24. Troubleshooting Workflow
    Check DNS config
Test nslookup
Check service
Check network
  25. Golden Debug Rule
    If service name fails → DNS issue or service missing
  26. Best Practices
    • Use service names instead of IPs
    • Verify namespace
    • Monitor DNS health
  27. Real-World Example
    • Frontend → backend via service name
    • Microservices discovery in Kubernetes
    • Dynamic scaling with DNS updates
  28. Summary
    Containers use internal DNS for service discovery, enabling dynamic and scalable communication between services in Docker and Kubernetes environments.
Completion check: You should now understand how container DNS enables service discovery in distributed systems.

Goal: Understand how port mapping works in containers and how to expose container services to the host and external networks.

  1. What is Port Mapping
    Port mapping connects a container port to a host port, allowing external access.
  2. Why Port Mapping is Needed
    • Containers are isolated
    • Need external access to services
  3. Basic Concept
    Host:8080 → Container:80
  4. Docker Port Mapping Syntax
    docker run -p HOST_PORT:CONTAINER_PORT image
  5. Example
    docker run -p 8080:80 nginx
    Access: 
    http://localhost:8080
  6. Multiple Port Mapping
    docker run -p 8080:80 -p 8443:443 nginx
  7. Bind to Specific IP
    docker run -p 127.0.0.1:8080:80 nginx
  8. Random Port Assignment
    docker run -P nginx
  9. Check Mapped Ports
    docker ps
  10. Inspect Port Mapping
    docker inspect container_id
  11. How It Works Internally
    • Uses NAT (iptables)
    • Host forwards traffic to container
  12. iptables Rule Example
    iptables -t nat -L
  13. Bridge Network Role
    • Container connected to docker0
    • NAT used for external access
  14. Host Mode vs Port Mapping
    • Host mode → no mapping needed
    • Bridge → requires mapping
  15. Expose vs Publish
    • EXPOSE → documentation
    • -p → actual exposure
  16. Docker Compose Example
    ports:
  - "8080:80"
  17. Security Considerations
    • Avoid exposing unnecessary ports
    • Use firewall rules
  18. Common Issues
    • Port already in use
    • Service not listening
    • Firewall blocking
  19. Debugging
    ss -tuln
docker ps
curl localhost:8080
  20. Check Container Service
    docker exec -it container_id netstat -tuln
  21. Test Connectivity
    curl http://localhost:8080
  22. Cloud Considerations
    • Open security groups
    • Check firewall rules
  23. Kubernetes Equivalent
    • NodePort
    • LoadBalancer
  24. Troubleshooting Workflow
    Check container running
Check port mapping
Check service inside container
Check firewall
  25. Golden Debug Rule
    If port mapped but not accessible → check service inside container
  26. Best Practices
    • Use specific ports
    • Limit exposure
    • Monitor open ports
  27. Real-World Example
    • Expose web app on port 80
    • Map API service to custom port
    • Run multiple services on same host
  28. Summary
    Port mapping allows container services to be exposed to the host and external systems, enabling real-world application access and communication.
Completion check: You should now understand how port mapping works and how to expose container services.

Goal: Understand how service discovery enables containers to communicate using names instead of IPs and how it works in Docker and Kubernetes.

    Service discovery allows services to find each other dynamically using names.

    • Services scale up/down
  3. Basic Concept
    Frontend → backend-service → resolved via DNS
  4. Types of Service Discovery
    • DNS-based
    • Service registry (Consul, etcd)
  5. DNS-Based Discovery
    • Most common
    • Automatic resolution
  6. Docker Service Discovery
    • Built-in DNS server
    • Service name = hostname
  7. Docker Example
    docker network create mynet
docker run --name db --network mynet mysql
docker run --network mynet app
    Access DB via: 
    db:3306
  8. Docker Compose Discovery
    • Service names become DNS names
  9. Kubernetes Service Discovery

    • Cluster-wide DNS
  10. Kubernetes DNS Format
    service.namespace.svc.cluster.local
  11. Example
    backend.default.svc.cluster.local
  12. Short Name Access
    backend
  13. Service Types
    • ClusterIP
    • NodePort
    • LoadBalancer
  14. Load Balancing via DNS
    • Returns multiple IPs
  15. Headless Services
    • No cluster IP
    • Direct pod access
  16. Service Registry Approach
    • Services register themselves
    • Clients query registry
  17. Overlay Network Role
    • Enables cross-node communication
  18. Benefits
    • No hardcoded IPs
    • Dynamic scaling support
  19. Common Issues
    • Name not resolving
    • Wrong namespace
    • DNS failure
  20. Debug DNS Resolution

dig service-name
  21. Check DNS Config

  22. Check Service

  23. Test Connectivity

Check service
Check network
Test connection
  26. Golden Debug Rule

  27. Best Practices
    • Use service names always
    • Avoid hardcoded IPs
    • Monitor DNS health
  28. Real-World Example
    • Frontend calls backend via service name
    • Microservices communicate dynamically
    • Auto-scaling updates DNS automatically
  29. Summary
    Service discovery enables containers to communicate using names instead of IPs, providing dynamic, scalable, and resilient communication in modern distributed systems.

Goal: Understand how Docker Swarm uses overlay networks to enable communication between containers across multiple nodes.

  1. What is Docker Swarm
    Docker Swarm is a container orchestration tool for managing clusters of Docker nodes.
  2. Why Overlay Networks in Swarm
    • Containers run on different hosts
    • Need seamless communication
  3. Basic Concept
    Node1 Container → Overlay → Node2 Container
  4. Swarm Architecture
    • Manager nodes
    • Worker nodes
  5. Overlay Network Creation
    docker network create -d overlay mynet
  6. Attach Service to Network
    docker service create --network mynet nginx
  7. VXLAN Technology
    • Encapsulates packets
    • Uses UDP port 4789
  8. Packet Flow
    Container → VXLAN encapsulation → Transport → Decapsulation → Container
  9. VNI (VXLAN Network Identifier)
    • Identifies overlay network
  10. Service Discovery
    • Built-in DNS
    • Service name resolution
  11. Load Balancing
    • Internal load balancing
    • VIP (Virtual IP)
  12. Ingress Network
    • Handles external traffic
  13. Routing Mesh
    • Requests can hit any node
    • Forwarded to correct container
  14. Encrypted Overlay
    docker network create -d overlay --opt encrypted mynet
  15. Multi-Host Communication
    • Containers behave as if on same network
  16. Inspect Network
    docker network inspect mynet
  17. Check VXLAN Interface
    ip link show
  18. Ports Used by Swarm
    • 2377 → cluster management
    • 7946 → node communication
    • 4789 → overlay network
  19. Common Issues
    • Firewall blocking UDP 4789
    • Nodes not connected
    • Overlay network not created
  20. Debug Overlay Network
    docker network inspect
ip route
tcpdump -i eth0 udp port 4789
  21. Check Node Status
    docker node ls
  22. Test Connectivity
    docker exec -it container ping other-container
  23. MTU Issues
    • Encapsulation reduces MTU
  24. Performance Considerations
    • Overlay adds overhead
  25. Security Considerations
    • Use encrypted overlay networks
  26. Troubleshooting Workflow
    Check nodes
Check network
Check ports
Capture packets
  27. Golden Debug Rule
    If overlay fails → check underlying network first
  28. Real-World Example
    • Microservices across multiple nodes
    • Distributed web applications
    • Cluster-wide service communication
  29. Summary
    Docker Swarm uses overlay networks to enable seamless communication between containers across multiple nodes, forming the backbone of distributed container networking.
Completion check: You should now understand how Docker Swarm overlay networking works for multi-node communication.
