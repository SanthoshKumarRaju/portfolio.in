Linux Process and Resource Management

•server
Summary

Linux process and resource management focuses on how the operating system handles running programs and allocates system resources like CPU, memory, and disk. It involves understanding how processes are created, monitored, prioritized, and terminated using various commands and signals. Tools such as ps, top, and htop help track system performance and identify issues. It also covers managing services, controlling resource limits, and analyzing system bottlenecks. Overall, it enables efficient system administration and troubleshooting of performance-related problems.

Process & Resource

Goal: Understand what Linux processes are, how they are created, how they move through lifecycle states, and how process IDs (PID, PPID) work.

  1. What is a Process
    A process is a running instance of a program. Whenever you execute a command or start an application, Linux creates a process to run it.
    Examples of processes:
    • bash shell
    • nginx web server
    • docker daemon
    • system services
    Example:
    sleep 60
    This creates a process that runs for 60 seconds.
  2. Program vs Process
    A program is a static file stored on disk.
    Example:
    /usr/bin/python
    A process is the running instance of that program in memory.
    Example:
    python script.py
  3. Viewing Running Processes
    Use the following command:
    ps
    Example output:
    PID  TTY   TIME   CMD
    2043 pts/0 00:00  bash
    2101 pts/0 00:00  ps
  4. Process ID (PID)
    Each process in Linux has a unique identifier called PID.
    Example:
    PID = 2043
    View all processes:
    ps -e
    Example output:
    PID  TTY   TIME  CMD
    1    ?     00:01 systemd
    2043 pts/0 00:00 bash
    PID 1 is the first process started by the system.
  5. Parent Process ID (PPID)
    Each process has a parent process that created it.
    Check parent-child relationship:
    ps -ef
    Example output:
    UID      PID   PPID  CMD
    root     1     0     systemd
    santhosh 2043  1     bash
    Here:
    • PID 2043 was created by PID 1
  6. Process Hierarchy
    Processes are organized in a tree structure.
    Example:
    systemd (PID 1)
└── ssh
    └── bash
         └── vim
    View process tree:
    pstree
    Example output:
    systemd─┬─ssh
        └─bash──vim
  7. Process States
    Processes go through different states.
    Common states:
    • R → Running
    • S → Sleeping
    • T → Stopped
    • Z → Zombie
    Example:
    ps aux
    Example output:
    USER      PID  %CPU %MEM STAT COMMAND
    santhosh 2043 0.0   0.2   S   bash
    STAT column shows the state.
  8. Process Lifecycle
    Every process follows a lifecycle:
    Created
  ↓
Ready
  ↓
Running
  ↓
Waiting
  ↓
Terminated
    The Linux kernel scheduler manages these transitions.
  9. Zombie and Orphan Processes
    Zombie process:
    • completed execution
    • still exists in process table
    Example:
    STAT = Z
    Orphan process:
    • parent process terminated
    • adopted by systemd (PID 1)
  10. The Init/Systemd Process
    The first process started by Linux is: 
    systemd
    Check it:
    ps -p 1
    Example output:
    PID  TTY  TIME   CMD
    1    ?    00:01  systemd
    All processes originate from this process.
  11. Foreground vs Background (Intro)
    Foreground process:
    • runs in terminal
    • blocks input
    Example:
    ping google.com
    Background process:
    ping google.com &
    Runs without blocking terminal.
  12. Why Process Management Matters
    Understanding processes helps in:
    • troubleshooting applications
    • monitoring system performance
    • managing services
    • debugging production issues
    Every running system depends on process management.
Completion check: You should now understand Linux processes, process IDs (PID, PPID), lifecycle, states, and process hierarchy.

Goal: Understand how to run and control processes in the foreground and background using Linux job control commands.

  1. What is Foreground and Background Execution
    When you run a command in Linux, it runs in the foreground by default.
    Foreground process:
    • runs in terminal
    • blocks user input
    Background process:
    • runs in background
    • does not block terminal
  2. Running a Foreground Process
    Example:
    ping google.com
    This command keeps running and blocks the terminal.
    To stop it:
    Ctrl + C
  3. Running a Background Process
    To run a command in the background:
    ping google.com &
    Example output:
    [1] 2345
    Meaning:
    • [1] → Job ID
    • 2345 → Process ID (PID)
  4. Viewing Background Jobs
    To list running background jobs:
    jobs
    Example output:
    [1]+ Running ping google.com &
  5. Bringing a Job to Foreground
    To bring a background job to foreground:
    fg %1
    This resumes job 1 in the terminal.
  6. Sending a Process to Background
    Step 1: Start a process
    ping google.com
    Step 2: Suspend it
    Ctrl + Z
    Example output:
    [1]+ Stopped ping google.com
    Step 3: Move to background
    bg %1
  7. Understanding Job IDs vs Process IDs
    Job ID:
    • used by shell
    • shown in jobs command
    Process ID (PID):
    • used by system
    • used in kill command
    Example:
    [1] 2345
  8. Stopping and Killing Jobs
    Stop foreground process:
    Ctrl + C
    Kill background job:
    kill %1
    Kill using PID:
    kill 2345
  9. Running Long Processes Safely
    If you close terminal, background processes stop.
    To avoid this, use:
    nohup command &
    Example:
    nohup python app.py &
    Example output:
    appending output to nohup.out
  10. Disowning Jobs
    To keep a process running after logout:
    disown %1
    This removes the job from shell control.
  11. Real DevOps Scenario
    Example:
    • deploying application
    • running script in background
    • monitoring logs
    Example command:
    nohup ./deploy.sh &
  12. Best Practices
    • use background jobs for long tasks
    • use nohup for persistent processes
    • monitor jobs using jobs command
    • kill unnecessary background processes
Completion check: You should now understand how to run and control foreground and background processes using job control commands.

Goal: Learn how to monitor running processes, analyze CPU and memory usage, and troubleshoot system performance using ps, top, and htop.

  1. Why Process Monitoring is Important
    Monitoring processes helps administrators:
    • identify high CPU usage
    • detect memory leaks
    • find stuck applications
    • troubleshoot system performance issues
    It is a core skill for DevOps and system administrators.
  2. The ps Command (Process Snapshot)
    The ps command shows a snapshot of running processes.
    Basic usage:
    ps
    Example output:
    PID   TTY   TIME   CMD
    2043 pts/0 00:00   bash
    2101 pts/0 00:00   ps
  3. Using ps aux (Detailed View)
    To view all processes:
    ps aux
    Example output:
    USER     PID  %CPU  %MEM  VSZ   RSS   TTY   STAT  START  TIME   COMMAND
root     1    0.0   0.1  22528  3200   ?     Ss   Mar15  0:01   systemd
santhosh 2043 0.1   0.3  50000  8000  pts/0  S    10:10  0:00   bash
    Important fields:
    • %CPU → CPU usage
    • %MEM → Memory usage
    • STAT → Process state
    • COMMAND → Running command
  4. Filtering Processes
    Find specific process:
    ps aux | grep nginx
    Example output:
    root 1023 0.0 0.2 nginx
  5. The top Command (Real-Time Monitoring)
    The top command shows real-time system activity.
    top
    Example output:
    PID   USER      %CPU  %MEM  COMMAND
2043  santhosh  2.5   1.2   bash
2100  root      10.0  3.5   nginx
    Key sections:
    • CPU usage
    • memory usage
    • running processes
  6. Understanding Load Average
    Top shows load average:
    load average: 0.50, 0.75, 1.00
    Meaning:
    • 1 min average
    • 5 min average
    • 15 min average
    Rule:
    • load = CPU cores → optimal
    • load > CPU cores → overloaded system
  7. Sorting Processes in top
    While running top:
    • Press P → sort by CPU
    • Press M → sort by memory
    This helps identify resource-heavy processes.
  8. The htop Command (Advanced UI)
    htop is an improved version of top.
    Install:
    sudo apt install htop
    Run:
    htop
    Features:
    • colorful interface
    • interactive process management
    • easy navigation
  9. Key Metrics in Process Monitoring
    Important metrics include:
    • CPU usage (%)
    • Memory usage (RSS)
    • Load average
    • Process state
    These help identify system performance issues.
  10. Monitoring Memory Usage
    Check memory usage:
    free -m
    Example output:
    total used free shared buff/cache available
8000  3000 2000 500    3000        4500
  11. Monitoring System Uptime
    Check uptime and load:
    uptime
    Example output:
    10:30 up 2 days, 3 users, load average: 0.50, 0.75, 1.00
  12. Real Production Scenario
    Example troubleshooting:
    • system is slow
    • run top
    • identify high CPU process
    • get PID
    • take action (kill or optimize)
  13. Best Practices
    • monitor systems regularly
    • track high resource usage
    • use htop for better visualization
    • analyze load averages
    These practices ensure stable systems.
Completion check: You should now understand how to monitor Linux processes using ps, top, and htop and analyze system performance.

Goal: Learn how to inspect processes efficiently using pstree, pidof, and pgrep to identify process relationships and locate processes quickly.

  1. Why Advanced Process Inspection is Needed
    Basic tools like ps show process lists, but in real systems:
    • there are hundreds of processes
    • process relationships matter
    • quick identification is required
    Advanced tools help:
    • visualize process hierarchy
    • search processes by name
    • identify parent-child relationships
  2. The pstree Command (Process Tree View)
    The pstree command displays processes in a tree structure.
    pstree
    Example output:
    systemd─┬─ssh
        ├─nginx───nginx
        └─bash───vim
    This shows how processes are related.
  3. Understanding Process Hierarchy
    Every process has a parent.
    Example:
    systemd (PID 1)
└── ssh
      └── bash
          └── python
    This hierarchy helps in debugging:
    • which service started the process
    • which user initiated it
  4. Using pstree with PIDs
    To display process IDs:
    pstree -p
    Example output:
    systemd(1)─┬─ssh(1020)
          └─bash(2043)──vim(2100)
  5. The pidof Command
    The pidof command finds the PID of a process by name.
    Example:
    pidof nginx
    Example output:
    1023 1024
    This shows all PIDs of nginx processes.
  6. Using pidof for Quick Identification
    Instead of:
    ps aux | grep nginx
    You can directly use:
    pidof nginx
    This is faster and cleaner.
  7. The pgrep Command
    The pgrep command searches for processes by name or pattern.
    Example:
    pgrep nginx
    Example output:
    1023
    1024
  8. Using pgrep with Patterns
    pgrep supports pattern matching.
    Example:
    pgrep python
    Find processes by user:
    pgrep -u santhosh
  9. Displaying Process Names with pgrep
    To show process name:
    pgrep -l nginx
    Example output:
    1023 nginx
    1024 nginx
  10. Combining Commands for Debugging
    Example workflow:
    • find process → pgrep
    • get PID → pidof
    • see hierarchy → pstree
    Example:
    pgrep nginx
    pstree -p
  11. Real DevOps Scenario
    Example:
    • application not working
    • find process → pgrep app
    • check parent → pstree
    • verify service origin
    This helps identify root cause quickly.
  12. Best Practices
    • use pstree for hierarchy debugging
    • use pidof for quick PID lookup
    • use pgrep for flexible searching
    • combine tools for troubleshooting
Completion check: You should now understand how to inspect processes efficiently using pstree, pidof, and pgrep in real Linux environments.

Goal: Understand how Linux uses signals to control processes and how to terminate or manage processes using kill, pkill, and killall.

  1. What are Signals in Linux
    Signals are messages sent by the operating system to processes.
    They are used to:
    • stop a process
    • pause execution
    • resume execution
    • terminate processes
    Signals allow communication between the kernel and processes.
  2. Common Linux Signals
    Important signals include:
    Signal Number Purpose
    SIGTERM 15 Graceful termination
    SIGKILL 9 Force kill
    SIGSTOP 19 Pause process
    SIGCONT 18 Resume process
    SIGHUP 1 Reload configuration
  3. The kill Command
    The kill command sends signals to processes.
    Basic usage:
    kill PID
    Example:
    kill 2043
    By default, this sends SIGTERM.
  4. Graceful vs Force Kill
    Graceful termination:
    kill -15 2043
    Force kill:
    kill -9 2043
    Difference:
    • SIGTERM → allows cleanup
    • SIGKILL → immediate termination
  5. Listing Available Signals
    To list all signals:
    kill -l
    Example output:
    1) SIGHUP 2) SIGINT 3) SIGQUIT 9) SIGKILL 15) SIGTERM
  6. Using pkill (Process Name)
    The pkill command kills processes by name.
    Example:
    pkill nginx
    This kills all nginx processes.
  7. Using killall
    The killall command also terminates processes by name.
    Example:
    killall python
    Difference from pkill:
    • killall matches exact process name
    • pkill supports patterns
  8. Sending Signals to Jobs
    You can send signals to background jobs.
    Example:
    kill %1
    This targets job ID 1.
  9. Stopping and Resuming Processes
    Pause process:
    kill -STOP 2043
    Resume process:
    kill -CONT 2043
    This is useful for temporarily suspending tasks.
  10. Real DevOps Scenario
    Example:
    • application consuming high CPU
    • find process using top
    • terminate process using kill
    Example:
    kill -9 2100
  11. Checking Process Before Killing
    Always verify before killing:
    ps aux | grep nginx
    Example output:
    root 1023 nginx
  12. Best Practices
    • use SIGTERM before SIGKILL
    • avoid killing critical system processes
    • verify PID before killing
    • use pkill carefully in production
Completion check: You should now understand how Linux signals work and how to control processes using kill, pkill, and killall.

Goal: Understand how Linux uses signals to control processes and how termination works internally from graceful shutdown to forced kill.

  1. What are Signals
    Signals are asynchronous messages sent to a process by:
    • the Linux kernel
    • other processes
    • user commands
    They are used to control process behavior such as:
    • termination
    • pause
    • resume
    • reload configuration
  2. Why Signals Exist
    Linux is a multi-process system.
    Signals provide a lightweight way to:
    • communicate with processes
    • control execution flow
    • handle unexpected events
  3. Common Linux Signals
    Signal Number Description
    SIGTERM 15 Graceful termination
    SIGKILL 9 Force kill
    SIGINT 2 Interrupt (Ctrl+C)
    SIGSTOP 19 Pause process
    SIGCONT 18 Resume process
    SIGHUP 1 Reload configuration
  4. Listing All Signals
    kill -l
    Example output:
    1) SIGHUP 2) SIGINT 3) SIGQUIT 9) SIGKILL 15) SIGTERM
  5. Graceful Termination (SIGTERM)
    Default signal sent by kill:
    kill 2043
    Equivalent:
    kill -15 2043
    Behavior:
    • process receives signal
    • performs cleanup
    • closes files
    • terminates safely
  6. Force Termination (SIGKILL)
    Force kill:
    kill -9 2043
    Behavior:
    • process is immediately terminated
    • no cleanup happens
    • cannot be intercepted
    Use only when necessary.
  7. Interrupt Signal (Ctrl + C)
    Pressing:
    Ctrl + C
    Sends:
    SIGINT (2)
    Used to stop foreground processes.
  8. Stopping and Resuming Processes
    Pause process:
    kill -STOP 2043
    Resume process:
    kill -CONT 2043
    This is useful for temporary suspension.
  9. SIGHUP and Configuration Reload
    Some services reload configuration using SIGHUP.
    Example:
    kill -HUP nginx_pid
    Used in:
    • nginx
    • apache
    • system daemons
  10. Signal Handling (Advanced Concept)
    Processes can handle signals using signal handlers.
    Behavior:
    • ignore signal
    • handle signal with custom logic
    • terminate on signal
    Exception:
    • SIGKILL cannot be handled or ignored
  11. Process Termination Internals
    When a process receives a termination signal:
    Signal received
    ↓
Cleanup resources
    ↓
Close files
    ↓
Exit system call
    ↓
Process removed from memory
  12. Zombie Processes
    If parent does not collect child status:
    • process becomes zombie
    Example:
    STAT = Z
    These remain in process table until cleaned.
  13. Real DevOps Scenario
    Example:
    • application not responding
    • try graceful kill → SIGTERM
    • if fails → force kill → SIGKILL
    Example:
    kill -15 2100
    kill -9 2100
  14. Best Practices
    • always use SIGTERM first
    • use SIGKILL only if needed
    • verify process before killing
    • avoid killing system-critical processes
Completion check: You should now understand how Linux signals work, how processes terminate, and how to control them safely in production.

Goal: Understand how Linux schedules processes and how to control CPU priority using nice and renice commands.

  1. What is Process Scheduling
    The Linux kernel manages CPU allocation using a scheduler. Since multiple processes run at the same time, the scheduler decides:
    • which process runs
    • how long it runs
    • when it gets CPU time
  2. Understanding Process Priority
    Each process has a priority level that determines how much CPU time it gets.
    Higher priority:
    • gets more CPU time
    Lower priority:
    • gets less CPU time
  3. What is Nice Value
    Linux uses a value called nice value to define priority.
    Range:
    -20 → highest priority
  0 → default priority
19 → lowest priority
    Lower nice value = higher priority.
  4. Viewing Process Priority
    Check process priority using:
    ps -eo pid,ni,cmd
    Example output:
    PID  NI CMD
2043 0  bash
2100 5  python script.py
    NI = nice value.
  5. Starting a Process with nice
    You can set priority when starting a process.
    Example:
    nice -n 10 python script.py
    This starts the process with lower priority.
  6. Changing Priority Using renice
    To change priority of a running process:
    renice 5 -p 2043
    Example output:
    2043 (process ID) old priority 0, new priority 5
  7. Increasing Process Priority
    To give higher priority:
    renice -5 -p 2043
    Note:
    • only root can set negative nice values
  8. Viewing Priority in top
    Run:
    top
    Example output:
    PID   USER     PR  NI  %CPU COMMAND
2043  santhosh 20  0   2.0   bash
    Fields:
    • PR → priority
    • NI → nice value
  9. Real DevOps Scenario
    Example:
    • heavy batch job consuming CPU
    • reduce its priority
    Command:
    renice 15 -p 2100
    This allows critical services to run smoothly.
  10. CPU Scheduling Behavior
    Linux uses a scheduler to distribute CPU fairly.
    Factors include:
    • priority (nice value)
    • CPU usage history
    • process type
  11. Best Practices
    • lower priority for background jobs
    • higher priority for critical services
    • avoid excessive high-priority processes
    • monitor CPU usage regularly
  12. Production Example
    Example scenario:
    • database server → high priority
    • backup job → low priority
    Commands:
    nice -n 15 backup.sh
    renice -5 -p database_pid
Completion check: You should now understand how Linux process scheduling works and how to control CPU priority using nice and renice.

Goal: Learn how to monitor CPU, memory, disk usage, and system performance using Linux resource monitoring tools.

  1. Why Resource Monitoring is Important
    Linux systems run multiple applications simultaneously.
    Administrators must monitor system resources to:
    • detect performance issues
    • prevent system crashes
    • identify bottlenecks
    • ensure system stability
  2. Checking Memory Usage (free)
    The free command shows memory usage.
    free -m
    Example output:
    total used free shared buff/cache available
8000  3000 2000 500    3000        4500
    Explanation:
    • total → total memory
    • used → used memory
    • free → unused memory
    • buff/cache → cached memory
  3. Understanding Memory Usage
    Linux uses free memory for caching to improve performance.
    Important concept:
    • low free memory is normal
    • available memory is more important
  4. Monitoring CPU Usage (top)
    top
    Example output:
    %Cpu(s): 10.0 us, 5.0 sy, 85.0 id
    Explanation:
    • us → user CPU usage
    • sy → system CPU usage
    • id → idle CPU
  5. Load Average
    Check system load:
    uptime
    Example output:
    load average: 0.50, 0.75, 1.00
    Meaning:
    • 1 min, 5 min, 15 min averages
    Rule:
    • load ≈ CPU cores → optimal
    • load > CPU cores → overloaded
  6. Disk Usage Monitoring (df)
    Check disk space:
    df -h
    Example output:
    Filesystem Size Used Avail Use% Mounted on
/dev/sda1  40G  20G  18G    53%   /
  7. Directory Size Monitoring (du)
    Check folder size:
    du -sh /var/log
    Example output:

  8. Detailed System Stats (vmstat)
    vmstat 1

    procs memory swap io system cpu
r b swpd free buff cache si so bi bo in cs  us sy id

  9. Disk I/O Monitoring (iostat)
    iostat
    Example output:
    Device tps kB_read/s kB_wrtn/s

  10. Monitoring Open Files (lsof)
    lsof
    Shows files opened by processes.
    Useful for debugging file locks and resource leaks.
  11. Real DevOps Scenario
    Example:
    • system is slow
    • check CPU → top
    • check memory → free
    • check disk → df
    This helps identify root cause quickly.
  12. Best Practices
    • monitor system regularly
    • track CPU and memory trends
    • avoid disk full situations
    • use multiple tools together

Goal: Understand how Linux manages system services using systemd and how to control services using systemctl from basic operations to advanced configurations.

  1. What is systemd
    systemd is the default init system used in modern Linux distributions.
    It is responsible for:
    • starting system services during boot
    • managing background services (daemons)
    • handling system state and targets
    Check init system:
    ps -p 1
    Example output:
    PID TTY TIME   CMD
1    ?  00:01 systemd
  2. What is a Service (Daemon)
    A service is a background process that runs continuously.
    Examples:
    • nginx → web server
    • sshd → SSH access
    • docker → container runtime
    Services usually run without user interaction.
  3. The systemctl Command
    systemctl is used to control systemd services.
    Basic usage:
    systemctl [command] [service]
    Example:
    systemctl status nginx
  4. Checking Service Status
    systemctl status nginx
    Example output:
    ● nginx.service - A high performance web server
Loaded: loaded (/lib/systemd/system/nginx.service)
Active: active (running)
  5. Starting and Stopping Services
    Start service:
    sudo systemctl start nginx
    Stop service:
    sudo systemctl stop nginx
    Restart service:
    sudo systemctl restart nginx
    Reload configuration:
    sudo systemctl reload nginx
  6. Enabling and Disabling Services
    Enable service at boot:
    sudo systemctl enable nginx
    Disable service:
    sudo systemctl disable nginx
  7. Understanding Service States
    Common states:
    • active (running)
    • inactive (stopped)
    • failed
    Check failed services:
    systemctl --failed
  8. Listing Services
    List all services:
    systemctl list-units --type=service
    List all installed services:
    systemctl list-unit-files
  9. Understanding Unit Files
    Service configuration is defined in unit files.
    Location:
    /etc/systemd/system/
    /lib/systemd/system/
    Example file:
    nginx.service
  10. Structure of a Unit File
    Example:
    [Unit]
Description=My App

[Service]
ExecStart=/usr/bin/node app.js
Restart=always

[Install]
WantedBy=multi-user.target
    Sections:
    • [Unit] → metadata
    • [Service] → execution details
    • [Install] → boot configuration
  11. Creating a Custom Service
    Create service file:
    sudo nano /etc/systemd/system/myapp.service
    Example:
    [Unit]
Description=My Application

[Service]
ExecStart=/usr/bin/python3 app.py
Restart=always
User=santhosh

[Install]
WantedBy=multi-user.target
    Reload systemd:
    sudo systemctl daemon-reexec
    Enable service:
    sudo systemctl enable myapp
    Start service:
    sudo systemctl start myapp
  12. Viewing Service Logs
    Use journalctl:
    journalctl -u nginx
    Example output:
    Mar 17 nginx started successfully
    View real-time logs:
    journalctl -u nginx -f
  13. Targets (Runlevels Replacement)
    systemd uses targets instead of runlevels.
    Examples:
    • multi-user.target → CLI mode
    • graphical.target → GUI mode
    Check default target:
    systemctl get-default
  14. Service Dependencies
    Services can depend on other services.
    Example:
    After=network.target
    This ensures service starts after network is ready.
  15. Real DevOps Scenario
    Example:
    • deploy application as service
    • auto-start on reboot
    • monitor logs
    Commands:
    systemctl enable app
    systemctl status app
    journalctl -u app
  16. Best Practices
    • always enable critical services
    • monitor logs using journalctl
    • use Restart=always for production apps
    • validate service files before deployment
Completion check: You should now understand how systemd works, how to manage services using systemctl, and how to create and debug system services in production environments.

Goal: Learn how to identify and analyze system performance bottlenecks including CPU, memory, disk, and I/O issues in Linux systems.

  1. What is a Performance Bottleneck
    A bottleneck occurs when a system resource is overloaded and limits overall performance.
    Common bottlenecks:
    • CPU bound
    • Memory bound
    • Disk I/O bound
    • Network bound
  2. Step 1 — Check System Load
    Check system load:
    uptime
    Example output:
    load average: 2.50, 3.00, 3.20
    Rule:
    • load ≤ CPU cores → OK
    • load > CPU cores → overloaded
  3. Step 2 — Analyze CPU Usage
    top
    Example output:
    %Cpu(s): 90.0 us, 5.0 sy, 5.0 id
    Interpretation:
    • high user CPU → application load

  4. Step 3 — Identify High CPU Processes
    ps aux --sort=-%cpu | head

  5. Step 4 — Analyze Memory Usage
    free -m

    Key indicators:
    • low available memory

  6. Check Swap Usage

  7. Step 5 — Analyze Disk Usage
    df -h

  8. Step 6 — Disk I/O Bottleneck

Goal: Understand how to use Linux logs and debugging tools like journalctl and strace to diagnose and troubleshoot system and application issues.

  1. What is Logging in Linux
    Logging is the process of recording system and application events.
    Logs help administrators:
    • track system activity
    • debug errors
    • monitor security events
    • analyze failures
  2. Common Log Locations
    Linux stores logs in: 
    /var/log/
    Important log files:
    • /var/log/syslog → system logs
    • /var/log/auth.log → authentication logs
    • /var/log/nginx/ → web server logs
  3. Viewing Logs Using cat and less
    View log file:
    cat /var/log/syslog
    Better method:
    less /var/log/syslog
  4. Real-Time Log Monitoring
    tail -f /var/log/syslog
    Example output:
    Mar 17 systemd started nginx service
    Used to monitor live system activity.
  5. Filtering Logs
    Search logs:
    grep error /var/log/syslog
    Filter by keyword:
    grep ssh /var/log/auth.log
  6. What is journalctl
    journalctl is used to query logs managed by systemd.
    View logs:
    journalctl
  7. Viewing Service Logs
    journalctl -u nginx
    Example output:
    Mar 17 nginx started successfully
  8. Real-Time Logs with journalctl
    journalctl -u nginx -f
    This shows live logs for a service.
  9. Filtering Logs by Time
    journalctl --since "1 hour ago"
    This helps analyze recent issues.
  10. What is strace
    strace traces system calls made by a process.
    It shows:
    • file access
    • network calls
    • system interactions
  11. Tracing a Process
    strace -p 2043
    Example output:
    read(3, "...", 1024) = 512
write(1, "...", 512)
  12. Debugging a Hanging Process
    Steps:
    • find process → ps/top

    • attach strace → strace -p PID
  13. Combining Logs and strace
    Workflow:
    1. journalctl → check error
2. find PID → ps/top
3. strace → debug system calls
  14. Real DevOps Scenario
    Example:
    • service not starting
    • check logs → journalctl -u service
    • trace process → strace
  15. Advanced Debugging Insight
    Use logs for:
    • high-level errors
    Use strace for:
    • low-level system behavior
  16. Best Practices
    • always check logs first
    • use journalctl for systemd services
    • use strace for deep debugging
    • combine tools for effective troubleshooting

Goal: Understand how Linux controls resource usage using ulimit and cgroups, and how these mechanisms are used in production systems and containers.

  1. Why Resource Control is Important
    In multi-user systems, one process can consume excessive resources.
    Without limits:
    • system can crash
    • CPU can be exhausted
    • memory can be consumed
    • too many files can be opened
    Resource control ensures system stability.
  2. Introduction to ulimit
    ulimit controls resource limits for a user session.
    Check all limits:
    ulimit -a
    Example output:
    open files (-n) 1024
max user processes (-u) 4096
stack size (-s) 8192
  3. Common ulimit Parameters
    Option Description
    -n max open files
    -u max processes
    -f max file size
    -t CPU time
  4. Setting Temporary Limits
    Example:
    ulimit -n 200
    Verify:
    ulimit -n
    Example output:
    200
    Applies only to current session.
  5. Soft vs Hard Limits
    Soft limit:
    • default limit
    • can be changed by user
    Hard limit:
    • maximum allowed
    • only root can change
  6. Persistent Limits Configuration
    Edit file:
    sudo nano /etc/security/limits.conf
    Example:
    santhosh soft nofile 2048
santhosh hard nofile 4096
  7. PAM Enforcement
    Ensure limits are applied:
    cat /etc/pam.d/common-session
    Check:
    session required pam_limits.so
  8. Real Scenario — Prevent Too Many Processes
    Example:
    * hard nproc 100
    Prevents fork bomb attacks.
  9. Introduction to cgroups
    cgroups (Control Groups) manage resource allocation at a system level.
    They control:
    • CPU
    • memory
    • disk I/O
    Used by:
    • Docker
    • Kubernetes
  10. How cgroups Work
    Hierarchy:
    cgroup
└── process group
      └── resource limits
    Processes are grouped and limits are applied.
  11. Viewing cgroups
    ls /sys/fs/cgroup
    Shows available controllers.
  12. CPU Control with cgroups
    Example concept:
    • limit CPU usage for a process group
    Used in containers to prevent CPU hogging.
  13. Memory Control with cgroups
    Example:
    • limit memory usage
    • prevent system crashes
  14. Real DevOps Scenario
    Example:
    • container limited to 512MB RAM
    • CPU usage restricted
    Docker internally uses cgroups.
  15. Difference Between ulimit and cgroups
    ulimit cgroups
    per user/session per process group
    simple limits advanced control
    shell-based kernel-level
  16. Advanced Insight
    ulimit:
    • controls user-level limits
    cgroups:
    • controls system-level resource isolation
    Together they form a complete resource management system.
  17. Best Practices
    • set limits for shared systems
    • monitor resource usage
    • use cgroups for containers
    • avoid unlimited resource allocation
Completion check: You should now understand how Linux controls resources using ulimit and cgroups and how they are used in production systems.
