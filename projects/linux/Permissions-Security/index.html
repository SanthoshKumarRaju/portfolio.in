Linux Permissions & Security

•server
Summary

This section explains how Linux secures files and system resources using its built-in permission and access control mechanisms. It introduces the Linux permission model, including user, group, and others permissions, and demonstrates how read, write, and execute permissions control access to files and directories. The section also covers numeric and symbolic permission formats and how administrators modify permissions using commands such as chmod, chown, and chgrp. Advanced security concepts including special permissions (SUID, SGID, and the Sticky Bit) are explored to understand how privilege behavior works in Linux systems. It also introduces Access Control Lists (ACLs) for fine-grained permission management. By completing this section, learners will understand how to securely manage file access and apply best security practices for protecting Linux servers.

Permissions & Security

Goal: Understand how Linux controls access to files and directories using the user, group, and others permission model.

  1. Why Permissions Exist
    Linux is a multi-user operating system. Multiple users may access the same system simultaneously. To protect system resources, Linux implements a permission model that controls who can read, modify, or execute files.
    Permissions protect:
    • system files
    • user data
    • application configuration
    • security credentials
    Without permissions, any user could modify critical system files.
  2. Basic Permission Structure
    Every file and directory in Linux has three permission categories:
    • User (Owner)
    • Group
    • Others
    Each category has three possible permissions:
    • Read (r)
    • Write (w)
    • Execute (x)
  3. Viewing File Permissions
    Use the following command:
    ls -l
    Example output:
    -rw-r--r-- 1 santhosh devops 2048 Mar 10 notes.txt
    This output provides permission information.
  4. Understanding the Permission String
    Example: 
    -rw-r--r--
    Breakdown:
    Section Meaning
    - File type
    rw- Owner permissions
    r-- Group permissions
    r-- Others permissions
  5. Permission Meaning
    Read permission (r):
    • Allows reading file contents
    • Allows listing directory contents
    Write permission (w):
    • Allows modifying file content
    • Allows creating or deleting files inside directories
    Execute permission (x):
    • Allows running programs
    • Allows entering directories
  6. Example Permissions on Directories
    ls -ld /home
    Example output:
    drwxr-xr-x 5 root root 4096 Mar 10 /home
    Meaning:
    • Owner can read/write/enter directory
    • Others can read and enter
  7. Checking Current User
    whoami
    Example output:
    santhosh
    This shows the current user interacting with files.
  8. Checking User Groups
    Users belong to groups which define shared permissions.
    groups
    Example output:
    santhosh sudo docker devops
    Group permissions allow collaboration between users.
  9. How Permission Checks Work
    When a user tries to access a file, Linux checks permissions in order:
    1 → Owner permissions
    2 → Group permissions
    3 → Others permissions
    The system determines access based on the user's relationship to the file.
  10. Why This Model is Important
    The Linux permission model helps protect systems by controlling access. It ensures:
    • users cannot modify other users' files
    • applications cannot access restricted data
    • system integrity is maintained
    Permissions form the foundation of Linux system security.
Completion check: You should now understand how Linux uses the user, group, and others permission model to control access to files.

Goal: Learn how Linux represents file permissions using symbolic and numeric formats and how administrators modify permissions using the chmod command.

  1. Understanding Permission Representation
    Linux permissions can be expressed in two ways:
    • Symbolic format
    • Numeric (octal) format
    Both formats control the same permission system but use different representations.
  2. Symbolic Permission Format
    Symbolic permissions use letters to represent access rights.
    Example permission string:
    -rwxr-xr--
    Breakdown:
    Section Meaning
    r Read permission
    w Write permission
    x Execute permission
    - No permission
  3. Changing Permissions Using Symbolic Mode
    Permissions can be modified using the chmod command.
    Add execute permission:
    chmod u+x script.sh
    Remove write permission:
    chmod g-w file.txt
    Give read permission to others:
    chmod o+r file.txt
    Explanation:
    • u → user (owner)
    • g → group
    • o → others
    • a → all users
  4. Viewing Permission Changes
    ls -l script.sh
    Example output:
    -rwxr-xr-- 1 user devops 1024 Mar 12 script.sh
    This confirms that execute permission was added for the owner.
  5. Numeric Permission System
    Linux also represents permissions using numbers.
    Each permission has a numeric value:
    Permission Value
    Read (r) 4
    Write (w) 2
    Execute (x) 1
    These values are added together to form permission codes.
  6. Understanding Octal Permission Values
    Example permission:
    755
    Breakdown:
    • 7 → read + write + execute (4+2+1)
    • 5 → read + execute (4+1)
    • 5 → read + execute (4+1)
    Meaning:
    • Owner → full access
    • Group → read and execute
    • Others → read and execute
  7. Changing Permissions Using Numeric Mode
    Example:
    chmod 755 script.sh
    chmod 644 file.txt
    Example output:
    -rw-r--r-- 1 user user 512 notes.txt
    Explanation:
    • 6 → read + write
    • 4 → read only
  8. Common Permission Settings
    Permission Meaning
    777 Full access to everyone
    755 Owner full access, others read/execute
    644 Owner read/write, others read
    600 Owner only access
  9. Recursive Permission Changes
    To change permissions for an entire directory structure:
    chmod -R 755 project/
    This applies the permission change to:
    • the directory
    • all subdirectories
    • all files inside
  10. Security Considerations
    Incorrect permission settings can create security risks.
    Example insecure setting:
    chmod 777 file.txt
    This allows any user to modify the file.
    Best practice:
    • Use least privilege permissions
    • Avoid world-writable files
    • Restrict sensitive files to owners
Completion check: You should now understand how Linux permissions are represented using symbolic and numeric formats and how to modify them using the chmod command.

Goal: Understand special Linux permissions including SUID, SGID, and the Sticky Bit and how they modify the default permission behavior.

  1. Introduction to Special Permissions
    Linux provides three advanced permissions that extend the standard read, write, and execute permissions.
    These permissions are:
    • SUID (Set User ID)
    • SGID (Set Group ID)
    • Sticky Bit
    They are used for:
    • privilege delegation
    • shared directory management
    • security control
  2. Understanding SUID (Set User ID)
    SUID allows a program to run with the permissions of the file owner, instead of the user executing the program.
    Example:
    The passwd command allows users to change passwords.
    ls -l /usr/bin/passwd
    Example output:
    -rwsr-xr-x 1 root root 54256 Mar 10 /usr/bin/passwd
    Notice the s in the owner execute position.
    This means the program runs with root privileges.
  3. Setting SUID Permission
    To add SUID permission:
    chmod u+s program.sh
    Check permission:
    ls -l program.sh
    Example output:
    -rwsr-xr-x 1 user user 2048 program.sh
  4. Understanding SGID (Set Group ID)
    SGID allows files created inside a directory to inherit the directory's group ownership. This is useful for collaborative projects.
    Example:
    chmod g+s shared_project
    Check permissions:
    ls -ld shared_project
    Example output:
    drwxr-sr-x 2 user devops 4096 shared_project
    Files created inside will automatically belong to the group devops.
  5. SGID on Files
    When SGID is set on executable files, the program runs with the permissions of the file's group.
    Example:
    -rwxr-sr-x
    This is less commonly used compared to directory SGID.
  6. Understanding the Sticky Bit
    The Sticky Bit prevents users from deleting files that belong to other users inside a shared directory. This is commonly used in /tmp directories.
    Check /tmp permissions:
    ls -ld /tmp
    Example output:
    drwxrwxrwt 10 root root 4096 /tmp
    Notice the t at the end.
    Meaning:
    • users can create files
    • users cannot delete other users' files
  7. Setting Sticky Bit
    Add sticky bit to directory:
    chmod +t shared_folder
    Verify:
    ls -ld shared_folder
    Example output:
    drwxrwxrwt 2 user user 4096 shared_folder
  8. Numeric Representation of Special Permissions
    Special permissions can also be represented numerically.
    Permission Value
    SUID 4
    SGID 2
    Sticky Bit 1
    Example:
    chmod 4755 program
    Meaning:
    • 4 → SUID
    • 755 → normal permissions
  9. Common Permission Examples
    Permission Meaning
    4755 SUID enabled
    2755 SGID enabled
    1777 Sticky bit enabled
    Example:
    chmod 1777 shared_directory
  10. Security Risks of SUID
    Programs with SUID can become security risks if misconfigured. Attackers may exploit SUID programs to gain elevated privileges.
    Find all SUID files:
    find / -perm -4000 2>/dev/null
    Example output:
    /usr/bin/passwd
    /usr/bin/sudo
    /usr/bin/chsh
    Administrators must monitor these files carefully.
  11. Best Practices for Special Permissions
    System administrators should follow these guidelines:
    • Use SUID sparingly
    • Audit SUID binaries regularly
    • Use sticky bit on shared directories
    • Use SGID for collaborative environments
    These practices help maintain secure Linux systems.
Completion check: You should now understand how SUID, SGID, and Sticky Bit modify Linux permission behavior and how they are used in real Linux environments.

Goal: Understand how Linux assigns file ownership and how administrators manage ownership using commands such as chown and chgrp.

  1. What is File Ownership
    Every file and directory in Linux has an owner and a group. Ownership defines who controls access to the file.
    Linux tracks two main ownership attributes:
    • User (owner)
    • Group
    Example file information:
    -rw-r--r-- 1 santhosh devops 1024 Mar 12 notes.txt
    Explanation:
    • santhosh → file owner
    • devops → group owner
  2. Viewing File Ownership
    To view ownership details:
    ls -l
    Example output:
    -rw-r--r-- 1 santhosh devops 512 Mar 12 project.txt
    The columns show:
    • owner username
    • group name
  3. Changing File Owner Using chown
    The chown command changes file ownership.
    Example:
    chown alice file.txt
    This changes the owner of the file to alice.
    Verify:
    ls -l file.txt
    Example output:
    -rw-r--r-- 1 alice devops 512 Mar 12 file.txt
  4. Changing Owner and Group Together
    You can modify both owner and group in one command.
    chown alice:developers file.txt
    Verify:
    ls -l file.txt
    Example output:
    -rw-r--r-- 1 alice developers 512 Mar 12 file.txt
  5. Changing Group Ownership
    To change only the group owner, use the chgrp command.
    chgrp devops project.txt
    Verify:
    ls -l project.txt
    Example output:
    -rw-r--r-- 1 santhosh devops 1024 Mar 12 project.txt
  6. Recursive Ownership Changes
    When managing directories, administrators often need to change ownership for all files inside.
    Use the recursive flag:
    chown -R alice:developers project_folder
    This changes ownership for:
    • the directory
    • all subdirectories
    • all files inside
  7. Checking User and Group Information
    To check current user:
    whoami
    Example output:
    santhosh
    To check group memberships:
    groups
    Example output:
    santhosh sudo docker devops
    These groups determine group-level permissions.
  8. Understanding Root Privileges
    Only the root user (administrator) can change ownership of files.
    Example command requiring root:
    sudo chown alice file.txt
    Regular users can only change permissions of files they own.
  9. Ownership in Shared Environments
    In collaborative environments, group ownership is often used to allow multiple users to access the same project files.
    Example:
    drwxrwsr-x 5 alice devops project_folder
    The group devops can collaborate on files within this directory.
  10. Security Best Practices
    Proper ownership management helps protect system integrity.
    Best practices include:
    • Assign correct file ownership
    • Restrict sensitive files to root
    • Avoid shared ownership unless necessary
    • Use groups for team collaboration
    Correct ownership prevents unauthorized access or modification.
Completion check: You should now understand how Linux assigns file ownership and how to manage owners and groups using chown and chgrp.

Goal: Understand Access Control Lists (ACLs) and how they provide advanced permission control beyond the standard Linux user, group, and others permission model.

  1. What are Access Control Lists
    The traditional Linux permission system supports only three permission levels:
    • User (owner)
    • Group
    • Others
    However, modern systems often require more flexible access control. ACLs allow administrators to assign permissions to:
    • multiple users
    • multiple groups
    • specific individuals
    This allows fine-grained security control for shared environments.
  2. Checking if ACL is Enabled
    Most modern Linux filesystems such as ext4 support ACLs.
    Check mount options:
    mount | grep acl
    If ACL support is enabled, the filesystem will allow ACL permissions.
  3. Viewing ACL Permissions
    To view ACL permissions, use the command:
    getfacl file.txt
    Example output:
    # file: file.txt
# owner: santhosh
# group: devops
user::rw-
group::r--
other::r--
    This shows the default Linux permission structure.
  4. Adding ACL Permissions
    ACL allows granting permissions to specific users.
    Example:
    setfacl -m u:alice:rw file.txt
    Meaning:
    • u → user
    • alice → username
    • rw → read and write permission
    Now user alice can access the file.
  5. Verifying ACL Changes
    getfacl file.txt
    Example output:
    # file: file.txt
# owner: santhosh
# group: devops
user::rw-
user:alice:rw-
group::r--
mask::rw-
other::r--
    Notice the new ACL entry for the user alice.
  6. Adding Group ACL Permissions
    ACL permissions can also be assigned to groups.
    Example:
    setfacl -m g:developers:rwx project.txt
    This grants read, write, and execute permissions to the developers group.
  7. Default ACLs for Directories
    ACLs can also define default permissions for new files inside directories.
    Example:
    setfacl -d -m u:alice:rwx project_folder
    Meaning:
    • new files inherit permissions
    • alice automatically gets access
    This is useful for shared development environments.
  8. Removing ACL Permissions
    To remove a specific ACL entry:
    setfacl -x u:alice file.txt
    Verify removal:
    getfacl file.txt
  9. Removing All ACL Permissions
    To clear all ACL entries:
    setfacl -b file.txt
    This restores the default permission model.
  10. Understanding the ACL Mask
    ACL includes a mask value which limits effective permissions.
    Example:
    mask::rw-
    The mask defines the maximum permission allowed for ACL users and groups. Even if an ACL entry grants full access, the mask may restrict it.
  11. ACL Indicators in File Permissions
    When ACL is enabled on a file, the permission output shows a "+" sign.
    Example:
    ls -l file.txt
    Example output:
    -rw-rw-r--+ 1 santhosh devops 1024 file.txt
    The "+" indicates that ACL permissions exist.
  12. Real-World Usage of ACLs
    ACLs are widely used in enterprise environments. Examples include:
    • shared project directories
    • application log access
    • data storage systems
    • multi-user development environments
    They provide flexibility that the standard permission model cannot.
  13. Security Best Practices for ACLs
    When using ACLs, administrators should follow these practices:
    • avoid overly permissive ACL entries
    • regularly audit ACL permissions
    • combine ACLs with standard permissions
    • document ACL usage in shared systems
    Proper ACL configuration improves security while maintaining usability.
Completion check: You should now understand how Linux ACLs extend the traditional permission model and allow fine-grained access control for users and groups.

Goal: Learn best practices for securing Linux servers using proper permission management, user access control, auditing tools, and secure configuration.

  1. Why Linux Security Matters
    Linux servers power a large portion of the internet including:
    • cloud infrastructure
    • web servers
    • database systems
    • container platforms
    Improper security configuration can lead to:
    • unauthorized access
    • data breaches
    • system compromise
    System administrators must implement strong security practices.
  2. The Principle of Least Privilege
    One of the most important security principles is the least privilege principle. Users and applications should only receive the minimum permissions necessary to perform their tasks.
    Benefits:
    • reduces risk of accidental damage
    • limits impact of compromised accounts
    • protects sensitive system resources
    Example:
    Instead of giving full access:
    chmod 777 file.txt
    Use restrictive permissions:
    chmod 640 file.txt
    Only the owner and group can access the file.
  3. Securing Sensitive Files
    Certain files contain critical system information and must be protected.
    Examples include:
    • /etc/passwd
    • /etc/shadow
    • SSH private keys
    • configuration secrets
    Check shadow file permissions:
    ls -l /etc/shadow
    Example output:
    -rw-r----- 1 root shadow 1200 Mar 10 /etc/shadow
    Only privileged users can access this file.
  4. Managing User Accounts Securely
    Administrators must carefully manage system users.
    View users:
    cat /etc/passwd
    Example output:
    root:x:0:0:root:/root:/bin/bash
    santhosh:x:1000:1000:Santhosh:/home/santhosh:/bin/bash
    Create a new user:
    sudo useradd developer
    Set password:
    sudo passwd developer
    Remove unused users:
    sudo userdel developer
    Inactive or unused accounts can become security risks.
  5. Using sudo Instead of Root Login
    Direct root login should be avoided. Instead, administrators should use the sudo command.
    Example:
    sudo apt update
    The sudo configuration is stored in:
    /etc/sudoers
    Only trusted users should have sudo privileges.
    Check sudo permissions:
    sudo -l
    This allows users to perform administrative tasks while maintaining accountability.
  6. Securing SSH Access
    SSH is commonly used to access Linux servers remotely.
    Check SSH configuration:
    sudo nano /etc/ssh/sshd_config
    Common security improvements:
    • disable root login
    • change default SSH port
    • use key authentication
    Recommended security settings:
    PermitRootLogin no
    PasswordAuthentication no
    Restart SSH service:
    sudo systemctl restart ssh
    Using SSH keys instead of passwords greatly improves security.
  7. Using SSH Key Authentication
    Passwords are less secure than SSH keys.
    Generate SSH key:
    ssh-keygen
    Copy key to server:
    ssh-copy-id user@server
    This allows secure password-less authentication.
  8. Monitoring File Permissions
    Administrators should regularly audit system permissions.
    Find world-writable files:
    find / -perm -002 -type f 2>/dev/null
    Example result:
    /tmp/testfile
    World-writable files can be exploited by attackers.
  9. Auditing SUID Files
    SUID files allow programs to run with elevated privileges. Administrators should review them regularly.
    Find world-writable files:
    find / -perm -002 -type f 2>/dev/null
    Find SUID files:
    find / -perm -4000 2>/dev/null
    Example output:
    /usr/bin/passwd
/usr/bin/sudo
/usr/bin/chsh
    Unexpected SUID files may indicate security issues.
  10. Checking Open Network Ports
    Network services expose potential attack surfaces.
    Check listening services:
    ss -tulnp
    Example output:
    tcp LISTEN 0 128 0.0.0.0:22
tcp LISTEN 0 128 0.0.0.0:80
    Disable unnecessary services to reduce attack surface.
  11. Using Firewall Protection
    Linux systems often use firewalls such as ufw or iptables.
    Enable firewall:
    sudo ufw enable
    Allow SSH access:
    sudo ufw allow ssh
    Check firewall status:
    sudo ufw status
    Example output:
    Status: active
22/tcp ALLOW Anywhere
  12. Monitoring System Logs
    Logs provide critical information about system activity.
    View authentication logs:
    sudo tail /var/log/auth.log
    Example output:
    Failed password for user admin from 192.168.1.10
    Frequent failed login attempts may indicate attacks.
  13. Regular System Updates
    Keeping the system updated is critical for security.
    Update packages:
    sudo apt update
    Upgrade packages:
    sudo apt upgrade
    Updates patch security vulnerabilities in software packages.
  14. Using Security Auditing Tools
    Advanced security monitoring tools include:
    • auditd
    • fail2ban
    • chkrootkit
    • rkhunter
    • lynis
    • logwatch
    Example installing fail2ban:
    sudo apt install fail2ban
    This tool automatically blocks IP addresses that attempt repeated unauthorized logins.
  15. File Integrity Monitoring
    Tools can monitor changes to system files.
    Examples include:
    • AIDE
    • Tripwire
    These tools detect unauthorized modifications.
    Example installation:
    sudo apt install aide
  16. Container and Cloud Security
    In modern DevOps environments, Linux security extends to containers.
    Important security practices:
    • limit container privileges
    • use read-only filesystems
    • scan container images
    Example container security check:
    docker info
  17. Security Checklist for Linux Servers
    Administrators should follow a security checklist:
    • use strong passwords or SSH keys
    • restrict file permissions
    • audit SUID files
    • enable firewall
    • monitor system logs
    • apply security updates
    Following these practices significantly improves server security.
  18. Summary of Linux Security Practices
    Key security practices include:
    • apply least privilege permissions
    • protect sensitive files
    • disable root login
    • use SSH keys
    • audit file permissions
    • monitor system logs
    • install security tools
    • keep systems updated
    Following these practices helps protect Linux servers from unauthorized access and attacks.
Completion check: You should now understand the fundamental practices used to secure Linux servers and how permissions, user management, and auditing tools contribute to system security.
