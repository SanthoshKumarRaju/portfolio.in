Goal: Understand how VPCs isolate networks in cloud environments and provide secure, scalable networking for applications.

  1. What is a VPC
    A Virtual Private Cloud (VPC) is a logically isolated network within a cloud provider where you can launch resources.
  2. Why VPC
    • Network isolation
    • Security control
    • Custom networking
  3. Basic Concept
    Cloud → VPC → Subnets → Resources
  4. CIDR Block
    10.0.0.0/16
    Defines IP range for VPC.
  5. Subnets
    • Public subnet
    • Private subnet
  6. Public Subnet
    Has internet access via Internet Gateway
  7. Private Subnet
    No direct internet access
  8. Internet Gateway (IGW)
    Enables internet connectivity for VPC.
  9. NAT Gateway
    Private → Internet (outbound only)
  10. Route Tables
    Define traffic routing rules
  11. Example Route
    0.0.0.0/0 → IGW
  12. Security Groups
    • Instance-level firewall
  13. NACL (Network ACL)
    • Subnet-level firewall
  14. Stateful vs Stateless
    • Security Groups → Stateful
    • NACL → Stateless
  15. Elastic IP
    • Static public IP
  16. VPC Peering
    Connect two VPCs
  17. Transit Gateway
    • Hub for multiple VPC connections
  18. VPN Connection
    On-prem → VPC
  19. Direct Connect
    • Dedicated connection to cloud
  20. DNS in VPC
    • Internal DNS resolution
  21. Private Endpoints
    Access cloud services privately
  22. Load Balancer Integration
    Client → LB → VPC → Instances
  23. High Availability
    • Multi-AZ deployment
  24. Multi-Region Setup
    • Disaster recovery
  25. Monitoring
    • Flow logs
    • Cloud monitoring tools
  26. VPC Flow Logs
    Capture network traffic logs
  27. Common Issues
    • Routing misconfiguration
    • Security group blocking
    • Subnet mismatch
  28. Troubleshooting Flow
    Check route table
Check SG/NACL
Check subnet
Check logs
  29. Best Practices
    • Use private subnets
    • Restrict access
    • Enable logging
  30. Real-World Example
    3-tier architecture (Web → App → DB) inside VPC
  31. Summary
    VPC provides secure, isolated networking in the cloud, enabling scalable and highly available application architectures.
Completion check: You should now understand how VPCs isolate and manage networks in cloud environments.

Goal: Understand how subnets divide cloud networks into smaller segments for better organization, security, and scalability.

  1. What is a Subnet
    A subnet is a smaller network segment within a VPC, created by dividing a larger IP range.
  2. Why Subnets
    • Network segmentation
    • Security isolation
    • Efficient IP management
  3. Basic Concept
    VPC (10.0.0.0/16) → Subnets (10.0.1.0/24, 10.0.2.0/24)
  4. CIDR Subnetting
    10.0.0.0/16 → 256 subnets of /24
  5. Subnet Mask
    Defines network vs host portion.
  6. Types of Subnets
    • Public subnet
    • Private subnet
  7. Public Subnet
    Route → Internet Gateway
  8. Private Subnet
    No direct internet access
  9. Subnet Routing
    Subnet → Route Table → Destination
  10. Route Table Association
    Each subnet is linked to a route table.
  11. Availability Zones (AZ)
    • Each subnet belongs to one AZ
  12. High Availability
    Multiple subnets across AZs
  13. IP Address Allocation
    Instances get IPs from subnet range.
  14. Reserved IPs
    • Cloud providers reserve some IPs
  15. Subnet Size Planning
    • Depends on number of instances
  16. Security Groups
    Applied at instance level.
  17. NACL (Network ACL)
    Applied at subnet level.
  18. Stateful vs Stateless
    • SG → Stateful
    • NACL → Stateless
  19. Subnet Isolation
    Web → Public subnet
App → Private subnet
DB → Private subnet
  20. NAT Gateway Usage
    Private subnet → NAT → Internet
  21. Load Balancer Placement
    Public subnet → Load Balancer → Private instances
  22. Subnet Peering
    • Via VPC peering or routing
  23. DNS Resolution
    Internal communication within subnet.
  24. Monitoring
    • Flow logs
  25. Common Issues
    • IP exhaustion
    • Wrong route table
    • Blocked traffic
  26. Troubleshooting Flow
    Check subnet CIDR
Check route table
Check SG/NACL
Check connectivity
  27. Best Practices
    • Use multiple AZs
    • Separate tiers (web/app/db)
    • Plan IP ranges carefully
  28. Real-World Example
    3-tier architecture using public and private subnets
  29. Advanced Concept
    • Subnet per microservice
    • Zero trust networking
  30. Summary
    Subnets divide networks into smaller segments, improving security, scalability, and organization in cloud environments.
Completion check: You should now understand how subnets structure and secure cloud networks effectively.

Goal: Understand how Security Groups act as virtual firewalls to control inbound and outbound traffic for cloud resources.

  1. What is a Security Group
    A Security Group is a virtual firewall that controls traffic to and from cloud resources like virtual machines.
  2. Why Security Groups
    • Control access
    • Improve security
    • Restrict traffic
  3. Basic Concept
    Client → Security Group → Instance
  4. Inbound Rules
    • Control incoming traffic
  5. Outbound Rules
    • Control outgoing traffic
  6. Example Rule
    Allow TCP 22 from 0.0.0.0/0
  7. Default Behavior
    • All inbound → denied
    • All outbound → allowed
  8. Stateful Firewall
    • Return traffic automatically allowed
  9. Attach to Resources
    • EC2 instances
    • Load balancers
  10. Protocol Types
    • TCP
    • UDP
    • ICMP
  11. Port Ranges
    80 → HTTP
443 → HTTPS
22 → SSH
  12. Source/Destination
    • IP range (CIDR)
    • Another security group
  13. Security Group Referencing
    App SG → allow traffic from Web SG
  14. Use Case (Web Server)
    Allow 80/443 → public
Allow 22 → admin IP
  15. Use Case (Database)
    Allow 3306 → only from App SG
  16. Security Groups vs NACL
    • SG → Stateful
    • NACL → Stateless
  17. Multiple Security Groups
    • Can attach multiple SGs to one instance
  18. Evaluation Logic
    • Rules are allow-only
    • No explicit deny
  19. Logging
    • Use VPC Flow Logs
  20. Monitoring
    • CloudWatch
  21. Common Issues
    • Port blocked
    • Wrong CIDR
    • Missing rule
  22. Troubleshooting Flow
    Check SG rules
Check ports
Check source IP
Check logs
  23. Security Best Practices
    • Least privilege
    • Avoid 0.0.0.0/0 for sensitive ports
    • Use SG referencing
  24. Performance Impact
    • Minimal latency impact
  25. Advanced Concepts
    • Micro-segmentation
    • Zero Trust model
  26. Integration with Load Balancer
    Client → SG → Load Balancer → Backend SG
  27. Automation
    Terraform / Ansible manage SG rules
  28. Real-World Example
    3-tier architecture secured using separate SGs
  29. Summary
    Security Groups act as virtual firewalls, controlling traffic flow and securing cloud resources effectively.
Completion check: You should now understand how Security Groups secure cloud infrastructure using firewall rules.

Goal: Understand how Kubernetes networking enables seamless communication between pods, services, and external clients in a cluster.

  1. What is Kubernetes Networking
    Kubernetes networking defines how pods communicate with each other, nodes, and external systems.
  2. Core Requirement
    Any Pod → Any Pod (without NAT)
  3. Cluster Network Model
    Flat network where all pods can communicate directly.
  4. Pod Networking
    Each pod gets its own IP address.
  5. Pod-to-Pod Communication
    Pod A → Pod B (direct IP communication)
  6. Pod-to-Node Communication
    Pods communicate with node services via network interfaces.
  7. Container Network Interface (CNI)
    • Plugin system for networking
  8. Popular CNI Plugins
    • Calico
    • Flannel
    • Cilium
  9. Service Concept
    Service → Stable IP → Routes to Pods
  10. ClusterIP
    • Internal service communication
  11. NodePort
    External → NodeIP:Port → Pod
  12. LoadBalancer
    • Cloud load balancer integration
  13. ExternalName
    Maps service to external DNS.
  14. kube-proxy
    • Handles service routing
  15. Service Discovery
    service-name.namespace.svc.cluster.local
  16. DNS in Kubernetes
    CoreDNS provides internal DNS.
  17. Ingress
    External traffic → Ingress → Services → Pods
  18. Ingress Controller
    • Nginx Ingress
    • Traefik
  19. Network Policies
    Define allowed traffic between pods
  20. Default Behavior
    • All traffic allowed (if no policy)
  21. Restrict Traffic
    Allow only specific pods/services
  22. Pod CIDR
    IP range for pods.
  23. Service CIDR
    IP range for services.
  24. Overlay Networking
    • Encapsulation (VXLAN)
  25. Underlay Networking
    • Direct routing (Calico)
  26. Load Balancing
    Service → distributes traffic across pods
  27. Session Affinity
    Sticky sessions to same pod.
  28. Debug Commands
    kubectl get pods -o wide
kubectl get svc
kubectl describe svc
  29. Check Connectivity
    kubectl exec -it pod -- ping service
  30. Common Issues
    • Pods cannot communicate
    • Service not reachable
    • DNS resolution failure
  31. Troubleshooting Flow
    Check pods
Check services
Check DNS
Check network policy
Check CNI
  32. Security Consideration
    • Use Network Policies
  33. Performance Consideration
    • Overlay adds latency
  34. Advanced Concepts
    • Service Mesh (Istio)
    • eBPF (Cilium)
  35. Real-World Example
    Frontend Pod → Backend Service → Database Pod
  36. Summary
    Kubernetes networking enables seamless communication between pods and services using a flat network model, service abstraction, and flexible routing mechanisms.
Completion check: You should now understand how Kubernetes networking enables pod and service communication in a cluster.

Goal: Understand how CNI plugins manage networking in Kubernetes clusters, enabling pod communication, routing, and network policies.

  1. What is CNI
    CNI (Container Network Interface) is a standard that defines how networking is configured for containers.
  2. Why CNI Plugins
    • Kubernetes does not handle networking directly
    • CNI plugins implement networking
  3. Basic Concept
    Pod → CNI Plugin → Network → Other Pods
  4. Core Responsibility
    • Assign IP to pods
    • Enable pod-to-pod communication
    • Manage routing
  5. How CNI Works
    Pod created → kubelet calls CNI → network configured
  6. CNI Configuration Files
    /etc/cni/net.d/
  7. CNI Binaries
    /opt/cni/bin/
  8. Pod Network Setup
    Create veth pair → attach to bridge → assign IP
  9. Network Namespaces
    Each pod runs in its own network namespace.
  10. veth Pair
    Container ↔ Host network bridge
  11. Bridge Networking
    Pods connected via Linux bridge.
  12. Overlay Networking
    • Encapsulation (VXLAN)
  13. Underlay Networking
    • Direct routing without encapsulation
  14. Popular CNI Plugins
    • Calico
    • Flannel
    • Cilium
    • Weave
  15. Calico
    • Layer 3 routing
    • Network policies support
  16. Flannel
    • Simple overlay network
  17. Cilium
    • eBPF-based networking
  18. IP Address Management (IPAM)
    Assign IP from Pod CIDR
  19. Routing
    Pod → Node routing → Cluster routing
  20. Cross-Node Communication
    Pod (Node1) → Tunnel → Pod (Node2)
  21. Network Policies
    • Implemented by CNI plugins
  22. Security
    • Traffic filtering
  23. Performance Consideration
    • Overlay → slower
    • Underlay → faster
  24. Debug Commands
    kubectl get pods -o wide
ip a
ip route
  25. Check CNI Pods
    kubectl get pods -n kube-system
  26. Common Issues
    • Pods not getting IP
    • Cross-node communication failure
    • CNI plugin crash
  27. Troubleshooting Flow
    Check CNI pods
Check config files
Check routes
Check connectivity
  28. Advanced Concepts
    • eBPF networking
    • Service mesh integration
  29. Real-World Example
    Calico used for secure networking with network policies in production cluster
  30. Best Practices
    • Choose CNI based on use case
    • Enable network policies
    • Monitor CNI health
  31. Summary
    CNI plugins are responsible for Kubernetes networking, enabling pod communication, IP management, routing, and security across the cluster.
Completion check: You should now understand how CNI plugins manage networking in Kubernetes clusters.
